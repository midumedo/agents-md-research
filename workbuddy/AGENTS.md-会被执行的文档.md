# AGENTS.md：一份会被执行的文档

**2026-11-08**

---

## 一句话

文档的冗余是免费的，指令的冗余是收费的。

AGENTS.md 不是文档，是一段每轮都要执行、且会压过代码的指令。这一个事实，足以解释它全部的写作规则、维护方式和失败模式。

## 一、三个反常识的观察

### 1. 长度不是问题，"被执行的无关指令"才是

流传最广的建议是"越短越好，60 行最佳"。但有一组对照实验给出的结果是：**长度对成功率与成本都没有显著影响**（`2602.11988` 附录 B，按文件长度分箱后成功率与单任务成本无相关）。

（限定必须说清：这是 12 个 Python 仓库、4 个 agent、LLM 生成的文件；作者自己在局限性里承认，Python 在训练数据里太多，换成冷门栈结论可能反转。所以它推翻的是"越短越好"这条**普遍建议**，不是证明"长度无关"这条**普遍规律**。）

真正的成本来自另一处。同一组研究者把 LLM 生成的上下文文件按类别逐项删除，再重跑（对象仍是 LLM 生成文件，不是人写文件）：

| 删掉的类别 | CTXbench 成本 | CTXbench 准确率 | SWE-bench 成本 | SWE-bench 准确率 |
|---|---|---|---|---|
| 完整文件 | $0.4715 | 68.12% | $0.3272 | 54.36% |
| 删「测试」类 | **$0.3730**（p=0.023） | 66.67%（p=0.80） | **$0.2756**（p=0.0035） | 57.72%（p=0.099） |
| 删「概览」类 | $0.4027（p=0.24） | 62.32%（p=0.15） | $0.3018（p=0.10） | 54.20%（p=0.73） |

删掉"怎么跑测试"这一节，成本降 16–21%，准确率没有统计上的损失。原因很朴素：agent 本来就会跑测试；你把命令写进去，它照着多跑一遍。

**出处与限定**（这组数字必须连着引）：

- 来源：`2602.11988` 表 7，原文在 `refs/md/2602.11988.md:405`，讨论在 `:407`。
- 做法：用 GPT-5.4 把 LLM 生成文件里的某一类**整段删掉**，再用 GPT-5.2 重跑 SWE-bench 与 CTXbench。
- 限定一：对象是 **LLM 生成**的文件。人写文件没有共享类别，做不了同样的消融。
- 限定二：只测了 GPT-5.2 一个 agent。
- 限定三："无损"指**无统计显著变化**，不是"完全一样"：CTXbench −1.5pp（p=0.80），SWE-bench +3.4pp（p=0.099）——一个略降一个略升，都不显著。

这组数字能支持的是"这类指令在这类仓库里是净成本"；不能支持"所有测试说明都该删"——在测试命令不标准的仓库里，它可能正是那条不可推导的信息。

所以问题不是"文件多长"，是"有多少条指令被执行了、但对结果没有贡献"。

### 2. 它会被无条件执行，包括与代码冲突的时候

`2610.30571` 造了 40 个项目，让指令文件写一种约定、代码里用另一种（例如文件要求 logging、代码里全是 print）。320 次运行，**90.1% 的情况下 agent 跟文件走**。更刺眼的是：Claude Code 在 80 次里有 79 次**明确指出了**这个冲突，然后照样按文件执行。

这条把"文档腐烂"的后果改写了一遍：

- README 过期：读者看一眼代码就绕过去了，损失接近零。
- AGENTS.md 过期：agent 照做，把过时的约定重新写进新代码，**损失会复利**。

它不是"慢慢失效的说明书"，是"一直在下错命令的上级"。

### 3. 活文档只做三件事：削、迁、挂

我统计了四份高频维护文件（共 166 条提交）：`openai-agents-python` 46 条、`kimi-code` 50 条、`dsh` 100+ 条、`deer-flow` 58 条。

- **削**：`simplify agent instructions while preserving requirements`、`slim root AGENTS.md`、`prune redundant decision records`、`remove the tdd skill`
- **迁**：`move deep package docs to package guides`、`give architecture review rules a per-artifact home`
- **挂**：把规则挂到必然发生的动作上（提 PR、改 schema、加依赖、发布）

166 条里，**没有一条**是"补充项目概览""补充技术栈""补充目录结构"。

一次都没有。

至少在这四份里，概览类内容从来没有被维护过——立项时写一次，之后再没有任何事件会触发它更新。而规则型内容每周都有事故逼着它追加。

（普查数据可以对照：22,854 个仓库里，五分之四的指令文件在创建后被编辑过。所以文件是活的，但**被编辑的永远是规则，不是简介**。）

## 二、第一性原理：指令与文档的成本结构不同

这是全部差异的源头。把两者放在同一张表里：

| | 文档（README、docs/） | 指令（AGENTS.md） |
|---|---|---|
| 何时进入上下文 | 读者主动去读 | 每次会话自动加载 |
| 冗余的代价 | 0（没人读就是 0） | 每轮 token + 被遵循的步数 |
| 过期的代价 | 读者自行纠偏 | 被照做，写进新代码 |
| 未触发的规则 | 无成本 | 占预算，稀释其他规则 |
| 失效方式 | 安静退化 | 主动误导 |

四条推论：

1. **可推导的内容写进去是负收益。** agent 读一遍代码就知道的事，你写一遍，它多读一遍、还多信一遍。
2. **不可推导但从不触发的内容，也是负收益。** 它占着每轮的预算，并稀释真正要紧的那几条——遵守率随指令数均匀下降，加一条不会让别的条更容易被遵守（`2610.11007` 把这个形式化成了容量受限的组合优化）。
3. **只有"改变下一步动作"的句子有正收益。** 判断标准不是"对不对"，是"删了它，行为变不变"。
4. **长度本身不收费，被执行的无关指令才收费。** 这解释了为什么 431 行的 `adk-go` 是活的，而 96 行的 `gemini-cli` 是死的：前者每条都在拦一个具体的坑，后者大半是 agent 自己能查到的东西。

## 三、三条定律

### 定律一：反先验律

> 一条规则的价值 ≈ 它与"称职 agent 默认行为"的偏离度 × 它被触发的频率。

偏离度为零的规则，是纯成本；触发频率为零的规则，是纯负债。

用它检验常见内容：

| 内容 | 偏离度 | 结论 |
|---|---|---|
| "本项目用 TypeScript" | 0（读一眼就知道） | 删 |
| "写代码要写测试" | 0（默认就会） | 删 |
| "用 2 空格缩进" | 0（该交给 linter） | 删 |
| "测试里不要用 sleep 同步" | 高（默认会这么干） | 留 |
| "别跑 `npm run build`，会毁 HMR" | 高（默认会跑） | 留 |
| "migration 只增不改" | 高（默认会改） | 留 |
| "PR 标题格式 `[<pkg>] <title>`" | 高（推不出来） | 留 |

这不是我一个人的判断。`2606.15828` 在 100 个热门仓库里编目了 6 种"配置坏味道"，最常见的一种叫 **Lint Leakage**（把 linter 已经强制的规则再写一遍），出现在 **62%** 的文件里；其次是 Context Bloat（42%）与 Skill Leakage（35%）。换句话说，大部分文件最大的问题不是写错，是**写了不该由它写的东西**。

这也解释了 `2611.04367` 的发现：**条件句的遵守率明显低于祈使句与解释句**。"如果合适的话……"这种写法偏离度模糊，agent 倾向于按默认走——写了等于没写，还占了位置。

### 定律二：权威不对称

> 文件压过代码。所以它的错误不是"读不到"，而是"被照做"。

文档腐烂是安静退化，指令腐烂是主动误导。这决定了维护方式必须是**删除驱动**，而不是"想到了就补一条"。

数据侧的证据有两层。

第一层：官方那份 `AGENTS.md` 自 2025-08 首次提交后再未修改，同期 README 换过 logo、章程通过、站点在更新——只有规范文件没有维护者。它现在不是"历史文件"，是"一份 15 个月前下达、至今仍然生效的命令"。

第二层更要命：普查发现 **74.0% 的指令不给任何理由**。没有理由的规则无法被重新评估——下一个人看到"必须用 X"，既不知道当初为什么，也不知道现在还成不成立，只能继承。于是文件里堆积的不是规则，是**没人敢删的遗产**。

### 定律三：事故坐标系

> 层级不是目录结构的镜像，是事故的索引。

我比对了 8 份子目录文件与各自根文件的逐行重复率：**接近 0**（唯一例外 4%）。它们不复制父文件的结论，只追加本层的不变量。

层级越深，越只写"不变量 + 测试"：

- 根：标准命令（`dsh` 的 52 条外链指向规则的家）
- 包：本层独有的坑，每条挂一个 `postmortem` 链接（"这条规则是怎么来的"）
- 叶子：某个接口不能破的约束 + 对应的测试文件名（`deer-flow` 的 routers 文件 123 行，没有一句流程说明）
- 证据：事故记录本身

根文件指向"规则在哪"，包级文件指向"规则怎么来的"。事故没有消失，它下沉到离事故最近的那一层。

## 四、为什么 2025 年的模板失效了

官方 README 给的是这个模板：项目概览 / 构建与测试命令 / 代码风格 / 测试说明 / 安全考虑。

它的隐含假设是：**agent 什么都不知道，所以要告诉它一切。**

2026 年的现实是：模型变强了，默认行为变好了。它读得懂目录、找得到测试、知道要写测试、知道不要硬编码密钥。于是模板里"可推导"的那部分——概览、技术栈、目录、标准命令——从"有用"变成了"纯成本"。

**模型越强，能写的越少。** 不是因为文件不重要了，是因为"agent 会做错的事"这个集合在收缩，而收缩之后剩下的，全是仓库特有的、从代码里推不出来的东西：外部契约、历史事故、不可逆操作、非标准约定。

一个可证伪的预测：2027 年活得好的 AGENTS.md，会进一步向"伤痕清单"收敛——大部分是"不要做什么"和"去读哪个文件"，几乎没有"这是什么"。

## 五、"论文互相矛盾"多半是个伪问题

把 17 篇按证据强度分档之后（分档见 `refs/README.md`），所谓的"四派吵架"大部分消失了——他们测的不是同一个东西。

| 测什么 | 结论 | 出处 | 证据强度 |
|---|---|---|---|
| 任务成功率 | 无显著影响（LLM 生成 −0.5% / −2%，人写 +2.4%，p=21%） | `2602.11988` | 受控对照 |
| 正确性（等价检验） | 无显著影响（界在 10–15pp） | `2607.27250` | 受控对照，但界很宽 |
| 运行时间与 token | 下降（−28.64% / −16.58%） | `2601.20404` | **观察性关联**，10 仓库 124 PR，有混淆 |
| 成本 | 上升 20% / 23% | `2602.11988` | 受控对照 |
| 遵守率 | 上升（工具使用频次 2.5 倍，推理 token +22%） | `2602.11988` | 受控对照 |

前三列可以同时成立：**更听话、更费钱、结果没更好**。第四列（更省时）之所以看起来相反，是因为它是相关性，不是对照——有 AGENTS.md 的仓库，本来可能就维护得更好。

真正没解决的只剩一个问题：**在文档贫瘠或冷门生态里，结论会不会反转？** `2602.11988` 附录 B 给了线索（删掉全部文档后，LLM 生成文件 +2.7% 并超过人写），作者也在局限性里承认语言生态可能影响结论。这不是两派对立，是同一问题的最后一块还没人测。

还有两个必须写进结论的限定：

1. **语言生态。** 实验全在 Python 上做，而 Python 的工具链在训练数据里极多，模型可能本来就"知道"。作者自己在局限性里承认：换成冷门语言或工具链，结论可能反转。
2. **仓库信息密度。** 把所有文档从仓库里删掉之后，同一批 LLM 生成文件反而提升 2.7%，并且超过了人写文件。也就是说：**文件的价值取决于"仓库里已有的可发现信息"与"agent 默认行为"之间的差**。文档齐全的仓库里它是冗余，文档贫瘠的仓库里它是雪中送炭。

所以"AGENTS.md 有用吗"这个问题本身问错了。该问的是：**这个仓库里，有多少东西是 agent 推不出来、又必须知道的？**

## 六、一个可操作的判据

写之前，每条过三问；写之后，每季度过一问。

**写之前：**

1. agent 读了代码和文档，能不能自己得出？能 → 删（这是文档的内容，不是指令）。
2. 这条会不会改变它的下一步动作？不会 → 删（它会被执行，但不产生结果，只产生账单）。
3. 它上一次被触发是什么时候？想不起来 → 删（它是负债，不是保险）。

**写之后：**

> 最近三个月，这份文件被删过东西吗？

没有，就大概率已经死了。活文档的提交信息里一定有 `slim` / `simplify` / `remove` / `prune`。

## 七、三种文件的分工

这是我认为最该被说清、却最少被说清的一件事：

| | 回答什么问题 | 加载方式 | 可以冗余吗 |
|---|---|---|---|
| `docs/`、README | 这个世界是什么样 | 人主动读；agent 按需检索 | 可以，冗余几乎无成本 |
| **AGENTS.md** | **agent 的默认行为在这里是错的** | 每次会话强制加载 | **不可以，每条都收费** |
| `skills/` | 这类任务该怎么做 | 按需加载（先只读 name + description） | 可以，不占常驻预算 |

三者混用的后果，就是我那 24 份样本里最常见的病：把 `docs/` 的内容塞进 `AGENTS.md`，再把 `AGENTS.md` 的内容复制进每个子目录。

正确的做法是反过来的：**描述下沉到 docs，能力下沉到 skills，AGENTS.md 只留纠正。**

---

## 八、结论

AGENTS.md 的本质不是"给 agent 的说明书"，是**一份对默认行为的修正案**。

修正案有三条铁律：

1. 只写会被违反的（反先验）。
2. 只写付得起执行成本的（每条都收费）。
3. 只写还成立的（它压过代码，过期即误导）。

写它最难的部分不是写，是**删**——删掉那些"听起来很对、但删了行为不变"的句子。这件事没有终点，因为默认行为在变、仓库在变、事故在积累。一份健康的 AGENTS.md，应该像一块不断被冲刷的河床：形状一直在变，但每一道沟都是水冲出来的，没有一道是画上去的。
