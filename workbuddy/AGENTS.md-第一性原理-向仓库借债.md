## 引言

如果你在 2026 年打开一个稍有规模的开源仓库，大概率会看到一个叫 `AGENTS.md` 的文件。它通常长这样：一段项目简介，一棵目录树，一节"技术栈"，一节"代码风格"，一节"测试命令"，最后用几个加粗的 **IMPORTANT** 收尾。

这套写法流传极广。它出现在无数篇"AGENTS.md 最佳实践"的文章里，出现在各家工具的快速上手文档里，也出现在你同事昨天刚提交的那个 PR 里。

问题是：**这套写法从来没有被任何权威定义过，而且其中大部分内容已经被实验证明是无效的。**

本文想做的不是再写一份清单——市面上不缺清单，缺的是**判断清单对错的方法**。因为模型每几个月就换一代，任何一份具体的写法建议都在快速贬值；而如果你手里只有清单，你就只能等着下一篇文章来告诉你上一篇文章错了。

所以这篇文章会走另一条路：先把"AGENTS.md 到底是什么"这个前提拆掉，再用唯一一次严格对照实验说明哪些流行做法已经死了，然后从 LLM 与 agent 的工作机制出发，推导出**四条设计约束**和**四道过滤器**，最后用这套工具去审计 2025 年那份流传最广的清单，并给出 2026 年的写法。

贯穿全文的中心论点是这一句：

> **AGENTS.md 的每一条规则，都是在向仓库借债。**

一条规则之所以必要，是因为仓库在某个维度上对 agent 不可读：风格没被 lint 固化，测试不是一条命令，某个目录看起来没用其实在用，某个部署流程只活在一个人的脑子里。你写下的每一行，都是在为这处不可读打一张欠条。

于是有三条推论：

1. **文件的长度 = 仓库可读性缺口的长度。** 不是你的表达能力的长度，也不是你对项目的了解程度的长度。
2. **修好仓库的每一处，文件就该少一行。** 加一条 lint 规则、把测试收成一条命令、把架构决策写进 ADR——每做完一件，就有一张欠条到期。
3. **长期正确的形态是持续变薄，而不是持续完善。** 一份三年后还在变厚的 AGENTS.md，几乎一定意味着这个仓库三年没有变得更好读。

这个框架的价值在于它可以自我演化。当模型升级时，你不需要重新去查"最新最佳实践"，只需要重跑一遍同一个问题：**这条还欠着吗？**

过时的从来不是规则的内容，而是"债已经还了，欠条还贴在墙上"这件事。

## 1. 一个从未被定义的「事实标准」

### 1.1 治理事实，以及它的正确读法

先把可核查的部分摆清楚。

`AGENTS.md` 由 OpenAI 于 2025 年 8 月发布。2025 年 12 月 9 日，Linux 基金会宣布成立 **Agentic AI Foundation（AAIF）**，三个创始捐赠项目是 Anthropic 的 MCP、Block 的 goose，以及 OpenAI 的 AGENTS.md；白金会员包括 AWS、Anthropic、Block、Bloomberg、Cloudflare、Google、Microsoft 和 OpenAI（[Linux Foundation 新闻稿](https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation)）。

这是一个重要的事实：AGENTS.md 已经不是某家厂商的私有约定，而是与 MCP 同级的基金会项目。官网列出的支持工具超过 25 个，覆盖 Codex、Cursor、Copilot、Gemini CLI、Aider、Amp、Windsurf、Devin、Jules、Factory、Zed、goose、opencode 等（[agents.md](https://agents.md/)）。

官网同时声称它被"超过 6 万个开源项目"使用。这个数字的统计口径是 GitHub code search 的 `path:AGENTS.md NOT is:fork NOT is:archived`，**没有经过独立复核**，且会包含空文件、模板仓库和残留。

所以这个数字的正确用法只有一种：**它是采用度信号，不是有效性证据。**

这两件事在 2025 年被大量文章混为一谈。"六万个项目在用"说明的是社会扩散已经完成；它一个字都没有说明"写了之后 agent 变强了"。而后者才是你真正关心的问题——第 2 章会给出答案，那个答案和直觉相反。

### 1.2 规范真空

现在打开 `agents.md` 仓库的 README 原文。

它的全部内容是：一段定位说明（"Think of AGENTS.md as a README for agents"）、一个 minimal example、一段如何本地运行官网的说明（[README 原文](https://raw.githubusercontent.com/agentsmd/agents.md/main/README.md)）。

没有 spec。没有 schema。没有必填 frontmatter。没有优先级规则。没有合并语义。没有版本号。

这意味着两件事。

第一，**今天所有流传的 checklist 都是社区自发产物，没有任何制度背书。** 不存在"符合规范"这回事，因此也不存在"违反规范"这回事。你同事写的那份、某篇十万加文章推荐的那份、某个模板仓库里的那份，在制度上是完全平等的——它们都只是某人的意见。

第二，更微妙的一点：**官方那个 minimal example，和社区流传的写法并不一样。**

我把官方示例的三节抄在这里：

- **Dev environment tips**：`pnpm dlx turbo run where <project_name>`、`pnpm install --filter <project_name>`、`pnpm create vite@latest ...`
- **Testing instructions**：CI plan 在 `.github/workflows` 里；`pnpm turbo run test --filter <project_name>`；包根目录可直接 `pnpm test`；跑单个用例用 `pnpm vitest run -t "<test name>"`；"Fix any test or type errors until the whole suite is green"
- **PR instructions**：标题格式 `[<project_name>] <Title>`；提交前跑 `pnpm lint` 和 `pnpm test`

请注意这份示例里**没有**什么：没有项目简介，没有目录结构，没有技术栈声明，没有架构说明，没有代码风格约定。

它全部是**命令**，以及一条**完成判定**（"跑到全绿"）。

这不是巧合。这是全文后面所有推导的起点：**官方给的示例，本身就是一份命令清单加一条验收标准。** 而社区后来加进去的那一大半内容——概览、目录树、技术栈——恰好是第 2 章实验里被证伪的部分。

### 1.3 更麻烦的是：四家工具的加载语义互不等价

规范层是空的，那么语义层呢？语义层由各家实现自己定义，而它们并不一致。

| 工具 | 读取位置 | 合并方式 | 上限 / 特殊规则 |
|---|---|---|---|
| **Codex** | 全局 `~/.codex/`（`AGENTS.override.md` 优先，否则 `AGENTS.md`，只取第一个非空文件）+ 从项目根**逐级向下走到 cwd** | **全量拼接**，从根往 cwd 连，空行分隔；越靠近 cwd 越靠后，因而"覆盖"前者；每目录**最多取一个**文件 | `project_doc_max_bytes` 默认 **32 KiB**，达到即停止追加；可配 `project_doc_fallback_filenames` |
| **GitHub Copilot** | 仓库内**任意位置**，可多个 | **就近优先**：目录树中**最近的** `AGENTS.md` 生效 | 根目录的单个 `CLAUDE.md` / `GEMINI.md` 可作替代；个人 > 仓库 > 组织，但所有相关指令都会提供给 Copilot |
| **Claude Code** | cwd 及所有上级目录 | **拼接**（父目录全加载）；子目录**懒加载**，仅在读到该目录文件时才加载 | 默认只在 cwd 及上级**都不存在** `CLAUDE.md`、`.claude/CLAUDE.md`、`CLAUDE.local.md` 时才读 `AGENTS.md`（v2.1.277+）；建议每文件 < 200 行；> 4 MiB 整个跳过；**不读** `AGENTS.local.md`、`AGENTS.override.md`、`.agents/` |
| **Cursor** | 项目根与子目录 | 作为 `.cursor/rules` 的简化替代，纯 markdown、无 frontmatter | 无法用 globs 限定作用域；放进 `.cursor/rules` 的 `.md` 会被忽略（缺 frontmatter） |
| **官网自述** | —— | "agents automatically read the **nearest** file in the directory tree, so the closest one takes precedence" | —— |

表格里的每一格都可以在对应官方文档里查到（[Codex](https://developers.openai.com/codex/guides/agents-md)、[Copilot](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions)、[Claude Code](https://docs.claude.com/en/docs/claude-code/memory)、[Cursor](https://cursor.com/docs/rules)）。

现在把"拼接"和"就近优先"放在一起看，问题就出来了。

**官网说的"最近的那个生效"，和 Codex 的"全部拼起来、靠后的更强"，不是同一件事。** 前者是覆盖语义（只有一个赢家），后者是累积语义（全部都在上下文里，只是顺序不同）。同一份文件树，在这两种语义下会得到两种不同的系统提示词。

举个具体的例子。假设你有一个 monorepo：

```
/AGENTS.md              → "禁止使用 npm，一律用 pnpm"
/apps/web/AGENTS.md     → "本包必须用 npm，历史原因"
```

- **Codex**：两段都进上下文，`apps/web` 那段在后面。模型看到的是"禁止 npm"和"本包必须用 npm"并列，靠后的更强——但前面那条并没有消失，它还在竞争注意力。
- **Copilot**：只读最近的那个。模型只看到"本包必须用 npm"，根本不知道仓库层面有相反的规定。
- **Claude Code**：如果根目录存在 `CLAUDE.md`，`AGENTS.md` **完全不读**——上面两段一个字都进不了上下文。
- **Cursor**：支持根与子目录，但没有 globs，你无法表达"这条只在 `src/api/**` 生效"。

同一条规则，四种命运。

所以第一个结论是：**"一份 AGENTS.md 喂所有 agent"在分发层成立，在语义层不成立。** 文件名统一了，加载行为没有统一。你在根目录写的第 40 行，在 Codex 里是"覆盖者"，在 Copilot 里可能根本不会被读到，在 Claude Code 里可能连整个文件都没被打开。

这也解释了为什么大量团队会观察到"同一个文件在不同工具里效果不一样"——那通常不是模型差异，是加载差异。

### 1.4 表达力缺口

第二个结论关于能力边界。

`AGENTS.md` 是一种**无元数据的纯 markdown**。它无法表达作用域。你没有办法在文件里写"这一节只在 `src/api/**` 下生效"——因为没有任何工具会解析这句话。

而它的竞争者可以：

- **Cursor 的 `.cursor/rules/*.mdc`** 有 frontmatter，用 `alwaysApply` / `description` / `globs` 三个字段组合出四档触发：`alwaysApply: true` 恒生效；给 `globs` 则匹配文件时自动附加；只给 `description` 则由 Agent 自行判断相关性；三者都不给则只能 `@` 手动引用（[Cursor Docs](https://cursor.com/docs/rules)）。
- **Claude Code 的 `.claude/rules/` + `paths:`** 提供路径级规则，只在处理匹配文件时加载。官方文档特别指出：拆到 `@path` 导入**并不减少上下文开销**，因为被导入文件与导入它的文件一起加载；要真正省上下文，只能用路径级规则。

也就是说：**"一份文件"是 2026 年的可行下限，不是最优解。** 它适合"整个仓库共享的少量规则"；一旦你的规则开始出现"只在某处适用"的分化，纯 markdown 就会逼你把所有规则都塞进全局，而这正是下一章要付代价的地方。

### 1.5 换掉分析对象

到这里，前提已经拆完了：**没有规范，语义分裂，表达力受限。**

那么"最佳实践"从哪来？如果从惯例来，惯例已经被证明不可靠；如果从权威来，权威并不存在。只剩一条路：**从机制推导。**

但在推导之前，还得先换掉分析对象。

大多数人把 `AGENTS.md` 当成"文档"来想，于是它的成本被算成"写它花的时间"和"读起来累不累"。这个算法是错的。

正确的对象是：**每一轮 agent 循环中，被重复注入上下文的那一段 token。**

这个对象的成本结构完全不同：

```
总成本 ≈ 文件 token 数 × agent 步数
```

它是**乘出来的**，不是加出来的。第 2 章会给出实测：给 agent 加一份 LLM 生成的上下文文件，推理成本平均 **+20%**，交互步数平均 **+2.45**。这两个数字乘在一起，才是你真正支付的东西。

一旦换成这个对象，问题就变形了：**这条规则值得在每一步都重付一次吗？**

而"值得"的判据，只能是它偿还了仓库的哪一处不可读。

这就是债务。一张欠条，每轮计息。

**本文余下部分的路线**：第 2 章用唯一一次严格对照实验说明，流行写法里的哪一部分连利息都还不上；第 3 章从四条机制推出四道过滤器；第 4 章加上时间维度，解释为什么 2025 年写的东西现在不管用；第 5 章用这套工具逐条审计并解剖一份真实感的 120 行文件；第 6 章回答"那我该写多厚"；第 7 章给出 2026 年的具体形态和让它不倒的维护机制。

## 2. 唯一一次严格对照实验，推翻了流传最广的建议

### 2.1 这项研究为什么重要

关于 AGENTS.md 的效果，网上有大量经验之谈，但严格对照实验只有一个。

《Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?》，作者 Thibaud Gloaguen、Niels Mündler-Sasahara、Mark Niklas Müller、Veselin Raychev、Martin Vechev，arXiv:2602.11988，v1 于 2026 年 2 月 12 日提交，v3 于 2026 年 9 月 29 日修订（[arXiv](https://arxiv.org/abs/2602.11988)）。作者群来自 ETH Zurich 体系与 LogicStar。

它的摘要第一句就把问题说清楚了：

> "Although this practice is strongly encouraged by agent developers, there is currently no rigorous investigation into whether such context files are actually effective for real-world tasks."

而它的结论句是：

> "We find that providing context files does not generally improve task success rates, while increasing inference cost by over 20% on average... while instructions in the context files are well followed by coding agents, repository overviews, although popular and recommended by model providers, are not helpful. We conclude that while context files are useful for specifying non-standard coding practices, any attempts to improve performance should be rigorously evaluated before deployment."

最后半句是全篇最重要的一句，后面第 4、6 章都会回到它：**上下文文件对"非标准编码实践"是有用的。**

### 2.2 实验设计决定了它能证明什么

先看方法，因为方法决定了结论的适用边界。

- **四组 agent / 模型配置**：Claude Code + Sonnet-4.5、Codex + GPT-5.2、Codex + GPT-5.1-mini、Qwen Code + Qwen3-30B-coder。
- **两个基准**：SWE-bench Lite（300 个任务，来自流行仓库，**没有**开发者写的上下文文件）；CTXbench（论文自建，138 个实例，来自 12 个**确实有开发者提交上下文文件**的仓库）。
- **三种设置**：无上下文文件（None）、LLM 生成（LLM）、开发者手写（Dev）。
- **测量**：任务成功率、推理成本、交互步数、行为变化。

两个基准的分工是关键：SWE-bench 测的是"你凭空给 agent 加一份文件会怎样"，CTXbench 测的是"真实仓库里本来就有的文件到底有没有用"。后者更接近你的处境。

### 2.3 总体结果：没有提升，而且更贵

成功率方面（双侧 Cochran-Mantel-Haenszel 检验）：

| 基准 | 对比 | p 值 | 结论 |
|---|---|---|---|
| SWE-bench | 无文件 vs LLM 生成 | 0.87 | 不显著 |
| CTXbench | 无文件 vs LLM 生成 | 0.37 | 不显著 |
| CTXbench | 无文件 vs 开发者手写 | 0.21 | 不显著 |
| CTXbench | **LLM 生成 vs 开发者手写** | **0.038** | **显著** |

幅度上：LLM 生成的文件让 SWE-bench 成功率平均**下降 0.5%**，CTXbench **下降 2%**；开发者手写的文件**提升 2.4%**，但不显著。在 8 个可比设置中有 5 个出现了 LLM 生成文件导致性能下降。

成本方面：

| 指标 | 数值 | 显著性 |
|---|---|---|
| 推理成本（SWE-bench，LLM 生成） | **+20%** | p < 0.001 |
| 推理成本（CTXbench，LLM 生成） | **+23%** | p < 0.001 |
| 推理成本（CTXbench，开发者手写） | 至多 +19% | 显著 |
| 交互步数（LLM 生成） | **+2.45 / +3.92** | 显著 |
| 推理 token（GPT-5.2，SWE-bench） | +22%（LLM 生成）/ +20%（手写） | —— |
| 推理 token（GPT-5.1-mini，SWE-bench） | +10%（LLM 生成）/ +2%（手写） | —— |

用债务的语言重述这张表：**借了债，没还上，还付了利息。**

而且利息部分是这张表里最硬的部分——成本与步数的 p 值都在 0.001 以下，远强于成功率的任何结论。即使未来有研究推翻"成功率无提升"，"成本显著上升"这一条也很难被推翻。

### 2.4 唯一一次显著：手写比 AI 生成好 7%

整篇论文只有一处统计显著：**开发者手写的文件，比 LLM 生成的文件高约 7%（p = 0.038）。**

这个数字的价值不在于"7%"，而在于它把问题从"要不要写"精确地转移到了"**写了什么**"。

因为如果上下文文件整体无效，那手写和 LLM 生成应该一样差；但它们不一样，且差异显著。这说明差异不在"有没有文件"，而在**文件里的内容类型**。

它也直接判了一类流行做法的死刑：让 agent 用 `/init` 之类的能力，从零生成一份 AGENTS.md。这条路生成的正是 LLM 生成那一组，而那一组显著更差。

后面第 3 章要给的四道过滤器，必须能解释这 7% 从哪来。如果不能，这套理论就是失败的。

### 2.5 概览消融：本章最值得细看的一段

"写项目概览、写目录结构"是流传最广的一条建议，也是模型厂商自己推荐过的。论文专门做了消融。

移除 `Overview` 类别后：

| 基准 | 完整文件 | 移除概览 | p 值 |
|---|---|---|---|
| CTXbench 准确率 | 68.12% | **62.32%** | 0.15 |
| SWE-bench 准确率 | 54.36% | **54.20%** | 0.73 |
| CTXbench 成本 | $0.4715 | $0.4027 | 0.24 |
| SWE-bench 成本 | $0.3272 | $0.3018 | 0.10 |

这里必须诚实：**"删掉概览准确率不降"这个说法是不准确的。** 在 CTXbench 上点估计掉了 5.8 个百分点，只是 p = 0.15，没有达到显著。SWE-bench 上几乎不动（−0.16pp，p = 0.73）。

所以正确的表述是：**在这两个基准上，无法证明概览有可检测的贡献。** 它不是"有害"，是"测不出好处"。

更有意思的是定位效率。论文发现上下文文件**并没有显著减少** agent 首次接触到被修改文件所需的步数；对 GPT-5.1-mini 甚至**显著增加**了步数，原因有两个：agent 会额外发出多条命令去找上下文文件，以及反复读取已经被注入上下文的文件。

也就是说，概览并没有帮 agent 更快地"看懂仓库"，它只是让 agent 多做了几件事。

而最漂亮的一个反向证据在附录里：**当上下文文件成为仓库的唯一文档来源时，LLM 生成的文件平均提升 2.7%，并且超过了开发者手写的文件。**

这个结果把机制讲透了：LLM 生成的文件主要是在**复述仓库里已有的文档**。当文档还在时，这些复述是纯冗余，占用注意力还有成本；当文档被删掉后，复述突然有了替代价值。

概览的价值不是"帮助理解"，是"替代文档"。一旦文档存在，它就是负资产。

### 2.6 关键线索：指令其实被很好地遵守了

如果成功率没提升，最自然的猜测是"agent 没照做"。论文否证了这个猜测。

它统计了工具提及对使用频率的影响：

| 工具 | 文件中提及时的平均调用次数 | 未提及时 |
|---|---|---|
| `uv` | 约 **1.6 次/实例** | **< 0.01 次** |
| 仓库特定工具 | 约 **2.5 次/实例** | **< 0.05 次** |

几乎只有被提及时才会被使用。行为层面也一致：有上下文文件时，agent 会运行更多测试、更多 `grep`、读写更多文件、更多使用仓库特定工具。

**所以 agent 很听话。它照着做了，做了更多事，花了更多钱，然后成功率没有变好。**

这条线索极其重要，因为它一次性否掉了一整类补救方案。如果问题是"没遵守"，那加大强调、加粗、全大写 **IMPORTANT** 是对的；但问题不是不遵守——问题在于**额外指令让任务本身变难了**（推理 token 上升 10%~22%，步数上升 2.45~3.92）。

第 4 章会展示，Anthropic 已经把"加 IMPORTANT 或全大写"明确列进了"可以停止做的事"。

### 2.7 一个必须交代的复杂性：长度不是主变量

这一节会稍微削弱本文自己的叙事，但我认为必须写，否则后面的处方就会变成它批判的那种东西。

论文还报告了一个结果：**上下文文件的长度与成功率、成本都没有相关性**（Figure 13）。

这条结论直接否证了"AGENTS.md 越短越好"的朴素版本。如果长度不是主变量，那么"砍到 100 行"这个动作本身并不带来收益。

正确的读法是这样的：

第一，样本内的长度范围是 24 到 2003 词（均值 641 词，约 9.7 个小节）。在这个范围内，长度不是主变量——**但这是在一个已经相对克制的区间内测出来的**，不能外推到一份 800 行的巨型手册。

第二，如果长度不重要而成本又确实上升了 20%，那么成本上升的来源就不是"字数"本身，而是**新增的、与任务无关的信息造成的干扰**。Chroma 的 Context Rot 研究给了直接支持：**仅仅加入 1 个干扰项，性能就低于基线；加入 4 个进一步恶化**（[Context Rot](https://research.trychroma.com/context-rot)）。

第三，因此真正的约束不是"字数"，而是"**无关信息的条数**"。这个精确化会直接进入第 3 章的规则 R1——它要求你砍的不是长度，是干扰项。

换句话说：一篇 300 行但每一行都在回答"这个仓库哪里不标准"的文件，可能比一篇 60 行但一半在讲"这是个 React 项目"的文件更健康。**长度是症状，不是病因。**

### 2.8 适用边界

最后交代边界，避免过度外推：

- 四组 agent/模型配置、两个基准，是**平均效应**研究，不是"每一条规则都无效"的证明。
- CTXbench 是论文自建的，虽然开源，仍存在构造者偏差的风险。
- 论文自己的结论是"上下文文件对**非标准编码实践**有用"，其余需要"rigorously evaluated before deployment"。这句话是后面所有"什么该留"讨论的文献锚点。
- 污染检查：按模型知识截止日期切分后，各模型在截止日期前的实例比例分别为 17%（Sonnet-4.5）、40%（GPT-5.2）、12%（GPT-5.1-mini / Qwen3-30B），**无显著差异**，不影响结论。

结论可以这样概括：**在主流 agent 与主流仓库上，一份"标准写法"的 AGENTS.md 测不出收益，但确实更贵；而它的内容类型决定了它是正资产还是负资产。**

那"什么类型"？这需要机制来解释。

## 3. 四条机制，四道过滤器

上一章留下的问题是：既然 agent 很听话、只是做了更多事却更没效率，那么"什么内容该留"的判据是什么？

网上流传的答案是"写短点"。这个答案太粗，粗到会导致两种相反的误操作：**误删本该保留的验证命令，误留本该迁出的硬约束。**

所以本章把"写短点"拆开。它其实是四条互不等价的设计约束，来自四个不同的机制，各自给出不同的处置动作。

### 3.1 机制一：注意力预算与干扰项

大模型不会均匀地使用上下文。

最经典的证据是《Lost in the Middle》（arXiv:2307.03172，TACL 2023）：当相关信息位于长上下文的首部或尾部时，模型表现最好；位于中段时显著退化。这是"位置效应"的原始出处。

但这里要谨慎：**这是一篇 2023 年的论文**，而 2026 年的模型上下文窗口普遍到了百万级，且训练方式已经改变。直接拿它当"现状"引用是不严谨的。它的价值在于提出了机制假设，而不是给出当前数值。

2025 年 Chroma 的《Context Rot》做了更大规模的复现与扩展：18 个模型、四家厂商、**194,480 次调用**、六类任务，每一类都刻意保持任务复杂度不变、只改变输入长度（[Context Rot](https://research.trychroma.com/context-rot)）。

三个结果值得记住。

**第一，长度增加导致性能持续下降，且是非均匀的。** 在 LongMemEval 上，所有模型在"聚焦输入"（约 300 token）上的表现都显著高于"完整输入"（约 113k token）。即便开启思考模式，最新模型仍有明显差距。

**第二，位置效应没有想象中那么强。** 在 NIAH 任务中，11 个"针"位置之间**未见显著差异**。这与《Lost in the Middle》的结论不完全一致——说明位置效应依赖于任务类型，不能当成普适规律。但在重复词任务中确实存在：异常词越靠近序列开头，定位准确率越高。

**第三，也是最反直觉的一条：结构连贯的输入，表现反而更差。** 在全部 18 个模型、全部针-干草堆配置下，**打乱句子顺序的干草堆一致优于保留逻辑连贯性的原文**。作者推测这与注意力机制如何受输入结构影响有关。

第三条对你的写法有直接影响：**"这份文档写得很顺、逻辑很清楚"不等于"模型更容易取用其中的信息"。** 一篇叙事流畅的架构说明，可能比一份条目化的命令清单更难被有效利用。这也从侧面解释了为什么官方那个 minimal example 是命令清单而不是散文。

还有一条与你的日常最相关：**干扰项的边际伤害非常大。** 在基线上仅加入 1 个干扰项，性能就低于基线；加到 4 个进一步恶化，且各干扰项的伤害不均匀。

把这条映射到 AGENTS.md 上：**文件里每一条与当前任务无关的规则，都是一个干扰项。** 你写"这个项目用 React"，在改一个 Python 脚本的任务里，它就是干扰项。

于是得到第一条设计规则：

> **R1（总量约束）：约束的对象不是字数，是无关信息的条数。**
> 判断标准不是"这行写得长不长"，而是"在一个与它无关的任务里，这行会不会成为干扰项"。会，就删。

这也解释了第 2 章那个看似矛盾的结果——长度与成功率无相关，但成本确实上升。因为伤害来自干扰项的**数量**，而不是字符的**总量**。一份 300 行但每行都只在特定场景下相关的文件，和一份 60 行但一半是通用废话的文件，伤害来源完全不同。

### 3.2 机制二：指令遵循有容量上限

第二个机制更硬：**同时生效的指令数量有上限，而且这个上限比你想的低得多。**

IFScale 基准用了一个很干净的实验：给模型一份商业报告写作任务，然后叠加最多 500 条"必须包含某个关键词"的指令，测模型能同时满足多少（[arXiv:2507.11538](https://arxiv.org/abs/2507.11538)）。

结果：**20 个前沿模型、7 家厂商，在 500 条指令的最大密度下，最好的模型也只有 68% 的准确率。**

而且论文明确指出存在**偏向靠前指令的偏差**，并把不同模型的退化模式分成三类（与模型规模和推理能力相关）。

这个数字对 AGENTS.md 的意义是：

**你的规则不是线性叠加的。** 写 10 条，每条大概 95% 被遵守；写 40 条，靠后的那些不是"遵守率降低"，而是**近乎不存在**。而且它们还在占用上下文、还在作为干扰项伤害前面的规则。

所以如果你数一下自己的 AGENTS.md，发现有 40 条"必须"和"禁止"，正确的理解不是"我有 40 条规则"，而是"**我有 40 个概率事件，其中一部分的触发概率接近零**"。

第二条设计规则：

> **R2（硬规则条数约束）：把"必须/禁止"的条数当成一个独立预算来管，而不是当成内容的副产品。**
> 如果你有超过 15 条硬规则，先假设其中一半不会被遵守——然后问：哪一半是我真的在乎的？

这条规则与 R1 的区别很重要：R1 管的是"无关信息"，R2 管的是"相关的规则太多"。它们伤害的机制不同（干扰 vs 容量竞争），处置也不同（R1 删，R2 排序并砍到能生效的数量）。

### 3.3 机制三：agent 的循环需要一个验证信号

前两条机制都在说"少写"。第三条反过来，说的是**必须写什么**。

Anthropic 在 Claude Code 的最佳实践里有一段话，我认为是全部材料里最锋利的一句：

> "Claude stops when the work **looks** done. If it has nothing to run that tells it whether the work actually **is** done, 'looks done' is all it has to go on. In practice that makes you the test suite, and every mistake sits there until you happen to notice it. If you give it something that comes back pass or fail, Claude can close that loop itself."
> （[Claude Code best practices](https://www.anthropic.com/engineering/claude-code-best-practices)）

翻译成机制语言：**agent 的循环需要一个终止条件，而模型自己无法判断"真的完成了"，只能判断"看起来完成了"。** 唯一能把这个判断从"看起来"变成"是"的东西，是一条能返回 pass/fail 的可执行检查。

紧接着的一句更直接：

> "If your repo already has one of these, **the single most useful line in your `CLAUDE.md` is the command that runs it.**"

这一条机制解释了三件事。

**第一，它解释了第 2 章那 7%。** 手写文件的人知道这个仓库该怎么验证——单文件测试怎么跑、类型检查用哪个命令、lint 的入口在哪。LLM 生成的文件不知道，它只能写"运行测试"这种无法执行的话。这 7% 不是文笔差异，是**验证信号的差异**。

**第二，它解释了为什么"写更多描述"是负收益。** 描述不改变终止条件。你写十句"请确保代码质量"，agent 的完成判定没有变；你写一行 `pnpm vitest run -t "<test name>"`，判定变了。

**第三，它给出了"什么该留"的最强判据。** 一条信息如果能改变 agent 判断"做完了没有"的依据，它的价值高于任何描述性文字。

第三条设计规则：

> **R3（验证优先）：文件中价值最高的一行，是那条能让 agent 自己判断成败的命令。**
> 如果一份 AGENTS.md 里没有任何可执行命令，它大概率在还一笔本可以不借的债。

### 3.4 机制四：指令层级决定强制力

前三条都在讨论"写多少、写什么"，第四条讨论"写了有没有用"——而答案取决于你把它写在哪一层。

Anthropic 把这个区分讲得极清楚：

> "**Non-deterministic**: you write the instruction, and Claude (the model) reads it. This can be your prompt, `CLAUDE.md`, or a skill. The model then decides what to do with this information. It usually follows your commands... but there's no *guarantee* that it'll follow your instructions. It can still decide not to do things, or do other things.
>
> **Deterministic**: you configure the instruction, and Claude Code (the harness) *has* to execute this. This can be a hook, a deny rule, or a managed setting. Claude Code applies this every time, no matter what the model decided to do."

同一份文档里还有一句更不留情面的：

> "If something has to happen every time, make it a hook, a deny rule, or a managed setting. `CLAUDE.md` is for guidelines, and Claude is allowed to decide a guideline doesn't apply."

Claude Code 的 memory 文档也确认了技术细节：`CLAUDE.md` 是**以用户消息的形式、在系统提示词之后投递的**，因此"不保证严格遵循"；要强制阻止某个操作，必须用 `PreToolUse` hook 或 `permissions.deny`。

把 IFScale 的 68% 和这里的 100% 放在一起看：

**自然语言规则的遵循率有一个远低于 100% 的上限，而 lint / CI / hook 的遵循率是 100%。这是数量级差异，不是程度差异。**

所以"永不提交带 `.env` 的改动"这句话，写在 AGENTS.md 里是一个 68% 上限下的概率事件；写在 `permissions.deny` 里是一个 100% 的物理约束。同一句话，两个位置，两种性质。

第四条设计规则：

> **R4（硬约束迁出）：凡是"零例外"的规则，都不属于 AGENTS.md。**
> 判据：如果这条规则被违反一次你就无法接受，那它必须变成 hook、deny rule、lint 或 CI 检查。

但 R4 有一个官方给出的反向警告，必须一起写进来，否则会走向另一个极端：

> "Whatever the scope, keep the enforced set small. Every hook and deny rule will occasionally fire when it shouldn't, and someone has to maintain each one. If you ever find yourself at forty of them, most are probably preferences that Claude could have weighed on its own."

也就是说，**R4 不是"把所有规则都变成 hook"，而是"把真正零例外的规则变成 hook"**。`Prefer named exports` 有很多例外，它就该留在文本里；`Never read .env` 没有例外，它就该走 deny rule。

### 3.5 四道过滤器

把四条机制收束成一张表，就是本文后面要反复使用的工具：

| 过滤器 | 判据 | 来自哪条机制 | 不满足时的处置 |
|---|---|---|---|
| **F1 不可推导性** | agent 能不能从仓库里自己获得？而且它**真的会去看**吗？ | 注意力预算（冗余 = 干扰项） | 删除 |
| **F2 决策相关性** | 这条信息是否改变 agent 的动作选择，或改变它判断"做完了"的依据？ | 指令容量上限 + 验证枢纽 | 删除 |
| **F3 低衰减性** | 这是本仓库/本组织的**私有事实**，还是关于模型/世界的**通用知识**？ | 模型演进与信息半衰期 | 删除，或改写成私有事实 |
| **F4 不可机械化** | 能不能被 lint / 类型 / CI / test / hook 强制？ | 指令层级（68% vs 100%） | 迁出到闸门 |

三条使用要点：

**第一，四者是「与」关系，不是「或」关系。** 一条规则必须同时通过四道才留在文件里。通过 F1 但不通过 F2，它是一条"agent 推不出来但也不影响行动"的冷知识，删。通过 F2 但不通过 F4，它是一条本该由机器执行的硬约束，迁。

**第二，处置动作不同，这是最容易漏掉的部分。** F1、F2 不通过是**删**；F3 不通过是**删或改写**（下一章会讲改写为什么重要）；F4 不通过是**迁出**，不是删。把 F4 当成删除，你会丢掉真正的约束；把 F1 当成迁移，你会把冗余搬到一个更贵的地方。

**第三，用债务的语言重述一遍，会更好记：**

- **F1 / F2 判断这笔债该不该借。**
- **F3 判断这笔债会不会自己消失。**
- **F4 判断该不该换个债权人。**

### 3.6 为什么必须拆成四条

如果只记住"要短"，你会做出两个必然的错误。

**错误一：删掉验证命令。** 因为验证命令往往很长（`pnpm turbo run test --filter <project_name> && pnpm lint ...`），在"追求短"的标准下它是首要删除对象。但在四过滤器下，它是唯一能通过 F2 且带来正收益的内容——第 2 章那 7% 就来自这里。

**错误二：留下硬约束。** "永不修改 `vendor/`"很短，很容易留下。但它应该走 F4 迁到 `permissions.deny`，因为留在文本里只有 68% 的把握。

"写短点"这个建议之所以流行，是因为它对**症状**有效（文件确实短了），对**病因**无效（干扰项没少、硬约束没迁、验证命令被误删）。而一个只对症状有效的处方，会在下一次模型升级时失效——这正是下一章要处理的问题。

## 4. 信息的半衰期：为什么你 2025 年写的规则现在不管用了

### 4.1 一个具体的困惑

很多人有过这个体验：2025 年精心写的 AGENTS.md，当时确实感觉 agent 变听话了；到了 2026 年，同样的文件，感觉它变成了背景噪音。

直觉的解释是"模型变了，我的文件过时了"。这个解释对，但没用——它只告诉你"要更新"，没告诉你**更新什么、为什么这一条过时而那一条不过时**。

如果所有规则都以同样的速度贬值，那你只能定期全部重写。但事实不是这样：**不同类型的指令，半衰期差两个数量级。**

### 4.2 四类信息，四条衰减曲线

| 类型 | 例子 | 半衰期 | 为什么 |
|---|---|---|---|
| **仓库私有事实** | "部署必须走 `make deploy-staging`，直连生产会被 WAF 拦"；"`legacy/` 目录看着没用，但报表任务在依赖它" | **≈ 无限** | 它不在任何公共语料里。模型再强也推不出来 |
| **组织约定** | 错误码前缀规范；PR 必须附迁移计划；哪个 error helper 是团队定的 | **慢衰减** | 除非约定本身变了，否则一直有效 |
| **通用世界知识** | "这是 React 项目"；"用 pytest 跑测试"；"目录结构如下" | **快衰减** | 模型每代更强，这类信息正从"有用"变成"冗余"，而冗余有成本 |
| **模型行为技巧** | "用 IMPORTANT 强调"；"你是资深工程师"；"先思考再回答" | **最快衰减** | 它们描述的是某一代模型的行为缺陷，而缺陷正在被修复 |

这张表能直接回答第 4.1 节的困惑：

**2025 年那些规则不是写错了，而是它们当初填的就是一个正在被模型自己填平的缺口。** 你没有做错判断，你只是没意识到那个缺口会合上。

而更麻烦的是第三种情况：**缺口合上了，欠条还贴在墙上。** 这时候它不再偿还任何东西，只剩成本——干扰项成本、注意力成本、以及"agent 过度应用这条规则"的成本。

### 4.3 衰减的机制根源

为什么衰减精确地沿着"私有 vs 通用"这条线发生？

因为模型能力提升的本质，是**把公共语料里的知识，从"需要外部注入"变成"已经在权重里"**。

一个 2023 年的模型需要你告诉它"pytest 是用来跑测试的"，因为它的训练数据里这类信息稀薄。一个 2026 年的模型不需要——它见过几百万个 Python 仓库，它知道 pytest 怎么用、目录通常怎么组织、React 项目长什么样。

但**你的部署流程不在公共语料里**。你的 WAF 规则、你的历史包袱、你们团队三年前那个决定——这些永远不会进权重。所以它们永远不会变成冗余。

于是得到一个可预判的判据：

> **半衰期 ≈ 所描述对象的变更频率 × 该知识在公共语料中的可得性**

- 两个都低（私有且稳定）→ 长期有效，放心写
- 两个都高（公共且易变）→ 现在就该删
- 一高一低 → **改写到低的那一侧**（这是下一节的重点）

### 4.4 最硬的证据：Anthropic 自己列的"过时"清单

上面这套是推导。有没有直接证据？有，而且是厂商自己给的。

Anthropic 在 Claude Code 最佳实践里维护了一张表，标题是 "The old advice"，逐条说明为什么它已经不适用了（[Claude Code best practices](https://www.anthropic.com/engineering/claude-code-best-practices)，2026 年 11 月抓取）。我把它完整列出来，因为这张表本身就是"共识半衰期以月计"的最好证明：

| 过时的建议 | 为什么过时了 |
|---|---|
| 上下文窗口是主要约束，要激进管理 | 当前模型多为百万级窗口，压缩自动发生，很少耗尽。任务间 `/clear` 仍值得做，但理由变成了"聚焦的上下文答案更好、更便宜" |
| 给 Claude 老是忽略的指令加 **IMPORTANT** 或全大写 | 旧模型有时需要强调。当前模型遵循平实表述，**堆叠强调大多会让 Claude 过度应用这条规则** |
| 用子 agent 保护上下文窗口 | 上下文耗尽已很少是问题。子 agent 仍适合并行、隔离噪音输出、独立审查，但每个都要额外 token |
| 把任务交给子 agent 以获得更好答案 | 同一任务交给子 agent 不会让答案更好。全新的审查者有用，是因为它没看过你的推理——这和"委托"是两件事 |
| 在提示里写 `think hard`、`think harder`、`be thorough` | 努力程度由 effort 设置控制。这些词只是普通提示文本，在 effort 设定内做微调，不是提高档位的关键词 |
| 告诉 Claude 继续、循环直到完成、别偷懒 | 当前模型通常会自己推进，这类话更可能导致**过度工作**而非修复停滞。给它一个可通过的检查才是对的 |
| **在 `CLAUDE.md` 里描述你的架构和文件布局** | **Claude 自己会读仓库。只写不在里面的东西。** |

最后一行是整张表里对你冲击最大的一条。**"写架构和文件布局"是 2025 年流传最广的建议之一，现在被厂商自己明确列为过时，理由只有一句：它自己能读到。**

而这张表还有一句结尾，我认为比表本身更重要：

> "If any other advice on this page ever starts to feel like busywork, that's probably a sign it belongs in this table too."
> （如果这页上任何其他建议开始让你觉得是在做无用功，那多半说明它也该进这张表了。）

这是一个厂商在承认：**它的建议也有半衰期，而且判断标准是"你有没有感觉在做无用功"。**

顺带一提，Anthropic 在同一份文档里给出了"什么值得写"的正向清单，恰好是四类：

1. **如何确认工作**：确切的 test / typecheck / lint 命令，以及如何跑单个测试文件
2. **代码会误导人的地方**：一个到处都是但新代码不能模仿的旧模式；一个看起来没用其实在用的目录
3. **不在仓库里的决定**：团队选了哪个 error helper、部署怎么走、什么需要迁移评审
4. **你已经纠正过两次的事**

把这四条与第 4.2 节的表对照：全部落在"私有事实"和"验证信号"两栏。**厂商给的正向清单和本文的推导完全吻合**，这是一个不错的一致性检验。

### 4.5 F3 不只会删，它还会改写

这是四过滤器里最容易被低估的一道。

F3 的处置不是只有"删除"。当一条信息属于"通用世界知识"时，它还有第二个选项：**改写成私有事实。**

对比一下：

| 原写法（通用知识，快衰减） | 改写后（私有事实，不衰减） |
|---|---|
| "用 pytest 跑测试" | "测试必须带 `--cov-fail-under=85`，CI 会拦；覆盖率不够时不要改阈值，补测试" |
| "遵循 PEP 8" | "行长上限 100 不是 79，因为我们在用 Black + Ruff，配置在 `pyproject.toml`" |
| "错误要处理好" | "所有对外错误必须用 `AppError`，带 `code` 字段；直接 `raise Exception` 会被 review 打回" |
| "写清晰的提交信息" | "提交信息必须 `type(scope): summary`，`type` 只允许 feat/fix/chore/refactor；CI 会校验" |

左边这些，模型本来就知道，写进去只是占用注意力；右边这些，模型永远推不出来，而且**越强的模型越能有效利用它们**。

所以 F3 的正确用法是：

> **不是问"这条对不对"，而是问"这条能不能改写成只有我们仓库才成立的版本"。**
> 能改写 → 留下改写后的版本。
> 不能改写（因为它本质上就是公共知识）→ 删。

这个动作把一条快衰减的规则，转成了不衰减的规则。它是全文里**唯一一个能让文件变好而不是变短**的操作。

### 4.6 反直觉：该删的和该留的会分化，而且方向相反

这是债务模型最不直观、也最重要的一处。

直觉上，模型变强了，AGENTS.md 应该整体变得不重要。但实际发生的是**分化**：

- **通用知识和行为技巧**：价值随模型变强而**下降**，直到变成负资产（干扰项）。
- **私有事实和验证命令**：价值随模型变强而**上升**——因为它们不衰减，而模型执行它们的能力在变强。

第二点是关键。同一张欠条，兑现能力在提高。

举个例子：你写"部署必须走 `make deploy-staging`"。2024 年的模型可能看到了也不照做，或者做了但顺序错；2026 年的模型看到这一行，会准确地执行、检查前置条件、在失败时读日志。**规则没变，它的回报率变了。**

所以"AI 越来越强，是不是不用写了"这个反问，答案是：**写什么变得更重要了，写多少变得不重要了。**

该留的那一小部分，收益在上升；该删的那一大部分，成本在上升。两条曲线方向相反，这就是为什么"持续变薄"不是一个审美主张，而是一个**结构性结论**。

### 4.7 顺带解释：为什么大厂经验不能照抄

第 4.2 节的表还能解释另一件事——为什么 OpenAI 那篇"约 100 行、只做地图"的经验，你不能直接搬。

因为那份文件里的"私有事实密度"和你的完全不同。他们的仓库是五个月、零手写代码、约百万行、约 1500 个 PR 的产物，配了自写 linter、CI 校验、doc-gardening agent。在这种仓库里，绝大多数"通用知识"已经被工具和文档吸收了，剩下的确实只需要一张地图。

而在一个测试都跑不起来的仓库里，"地图"指向的是一片空白——你等于把信息丢掉了，agent 从"读到错的"变成"什么都没读到"，而后者更糟，因为它连纠错的线索都没有。

这个差别会在第 6 章展开成一张成熟度模型。

### 4.8 一个必要的诚实标注

最后说明：**"半衰期"是本文提出的分析框架，不是既有术语，也没有直接的实证研究支持。**

它建立在三个可核查的基础上：

1. Anthropic 官方那张"过时建议"表（直接证据，但只覆盖一家厂商、一个时间点）；
2. 第 2 章论文的概览消融（间接证据：概览这类"通用描述"确实测不出收益）；
3. 模型能力提升的一般机制（推理，非实验）。

所以正确的用法是把它当成一个**决策启发式**，而不是一条定律。它的价值不在于精确预测某条规则还能活几个月，而在于迫使你在写下每一行时多问一句：**这行描述的东西，会不会被下一代模型自己学会？**

如果会，那它现在就只是一张临时欠条——而且是一张到期后你还得记着撕掉的欠条。

## 5. 逐条审计：三堆分类，与一份 120 行文件的解剖

### 5.1 把 2025 年的清单摊开

有了四道过滤器和时间维度，就可以做审计了。我把 2025 年流传最广的那批建议逐条过一遍，判定分成四堆。

**判定依据标注的是"证据日期"而不是"权威"**——因为这个领域的共识半衰期以月计，权威会过期，日期不会。

| 建议 | 判定 | 依据 | 证据日期 |
|---|---|---|---|
| 写项目概览 | **已被推翻** | 消融实验测不出贡献（p=0.15/0.73）；厂商明确列为过时 | 2026-02 / 2026-11 |
| 写目录结构 / 文件布局 | **已被推翻** | "Claude 自己会读仓库。只写不在里面的东西" | 2026-11 |
| 写技术栈声明 | **正在到期** | 属于通用知识，模型已能从 `package.json` / `pyproject.toml` 推出 | 2026 |
| 让 AI 用 `/init` 一键生成 | **已被推翻** | LLM 生成版比手写版低约 7%（p=0.038） | 2026-09 |
| 用 **IMPORTANT** / 全大写强化 | **已被推翻** | "堆叠强调大多会让 Claude 过度应用这条规则" | 2026-11 |
| 复制整份 style guide | **从未有证据** | "Use a linter instead"；"Agent 已经知道常见风格约定" | 2026-11 |
| 用"6 万项目在用"论证有效性 | **从未有证据** | 采用度是社会信号，不是效果证据 | 2025-08 起 |
| 写完整架构说明 | **从未有证据** | 且被厂商明确列为过时；与仓库文档冗余 | 2026-11 |
| 角色设定（"你是资深工程师"） | **正在到期** | 属于模型行为技巧，当前模型不需要 | 2026 |
| 写"不要修改 vendor/" | **仍成立，但需迁移** | 零例外规则应走 `permissions.deny` | 2026-11 |
| 写测试 / 验证命令 | **仍成立，且价值最高** | "CLAUDE.md 里最有用的一行就是跑它的命令" | 2026-11 |
| 写不在仓库里的决定 | **仍成立** | 厂商正向清单第 3 条；论文"非标准实践"结论 | 2026-11 / 2026-09 |

四堆的分布很有意思：**"已被推翻"和"从未有证据"加起来占了绝大多数，"仍成立"只剩两条半。**

而这两条半，恰好就是四过滤器的输出：一条验证命令（过 F2）、一批私有决定（过 F1+F3）、以及一批该迁走的硬约束（不过 F4）。

### 5.2 逐行解剖：一份 120 行的 AGENTS.md

只给结论学不会判断。所以下面做一次完整解剖。

> **说明**：这份文件是根据大量真实仓库的常见结构**合成的典型样本**，不是某个具体仓库的原文。它刻意包含了 2025 年最流行的所有段落，目的是让每一条判定都能被检验。

原文的九个段落，120 行。逐段判定如下：

| # | 段落 | 行数 | 判定 | 触发 | 处置目标 |
|---|---|---|---|---|---|
| 1 | 项目简介（"这是一个面向 XX 的 SaaS 平台…"） | 12 | **删除** | F1 + F3 | 无（README 已有） |
| 2 | 目录结构树（`src/`、`lib/`、`tests/` 各是干什么的） | 18 | **删除** | F1 | 无（`ls` 一次就有） |
| 3 | 技术栈与版本（React 18、TypeScript 5、Vite…） | 10 | **删除** | F3 | 无（`package.json` 是真相源） |
| 4 | 代码风格约定（命名、import 顺序、行长、注释） | 22 | **迁移** | F4 | lint 配置（ESLint/Ruff） |
| 5 | 测试与验证命令 | 8 | **保留 + 改写** | 过 F2 | 置顶，补单文件命令与期望输出 |
| 6 | 提交信息与 PR 规范 | 9 | **迁移** | F4 | commitlint + CI 模板 |
| 7 | "不要修改 `vendor/` 和 `migrations/`" | 6 | **迁移** | F4 | `permissions.deny` + CODEOWNERS |
| 8 | 架构决策与历史背景（为什么这样分层） | 20 | **迁移 + 留指针** | F1 | `docs/adr/`，文件里留一行链接 |
| 9 | "**IMPORTANT**：务必确保代码质量、遵循最佳实践…" | 15 | **删除** | F3 | 无（无法执行，且会过度应用） |

几处需要展开说明：

**第 4 段（代码风格，22 行）为什么必须迁，不能留？**
因为它是全文里"看起来最有用、实际最浪费"的一段。Cursor 的文档把这条写得很直接：**"Copying entire style guides: Use a linter instead. Agent already knows common style conventions."** 同一份文档的"要避免"清单里还有一条：**"Duplicating what's already in your codebase."**（[Cursor Docs](https://cursor.com/docs/rules)）

风格约定是典型的"通用知识 + 可机械化"。它同时不过 F3 和 F4，处置是迁移——而且迁移之后**遵循率从 68% 变成 100%**，这是全文性价比最高的一个动作。

**第 5 段（测试命令，8 行）为什么是唯一该加长的？**
因为它过 F2 且过 F4 的反面（无法完全机械化：CI 能拦"测试没过"，但拦不住"你根本没跑对那个测试"）。它应该被改写成这样：

```markdown
## 验证（先看这一节）

改完代码必须能通过以下检查，否则不算完成：

- 单文件：`pnpm vitest run src/foo/bar.test.ts`
- 单用例：`pnpm vitest run -t "should reject expired token"`
- 全量：`pnpm turbo run test --filter web && pnpm lint --filter web`
- 类型：`pnpm tsc --noEmit`

期望输出：全绿，0 error。失败时先看第一条 error 的文件与行号，
不要先改测试断言——先判断是实现错了还是断言错了。
```

注意最后一行的价值：它改变了 agent 在失败时的**动作选择**（先看实现还是先改断言），这是 F2 的典型通过案例。而"请确保代码质量"这种话，不改变任何动作。

**第 7 段（"不要修改 vendor/"）为什么是迁移而不是删除？**
因为它是一条真实约束，只是放错了层。它过 F2（确实改变动作）、过 F3（是本仓库私有事实），但不过 F4（可以机械化）。所以它该走 `permissions.deny`，或者至少 CODEOWNERS + CI 检查。

Anthropic 的判据在这里很好用：**"如果一条规则被违反一次你就无法接受，那它必须变成 hook 或 deny rule。"**

**第 9 段（IMPORTANT 那 15 行）为什么必须删？**
三个理由叠加：它无法执行（不过 F2）；它是模型行为技巧（不过 F3，且衰减最快）；它还可能有害——官方原话是"堆叠强调大多会让 Claude **过度应用**这条规则"。

也就是说，这 15 行不只是无效，它可能让你的 agent 变得**过度谨慎**，从而在简单任务上浪费步数。第 2 章那个"步数 +2.45"里，可能就有一部分来自这类文字。

### 5.3 解剖后的账目

把上面的处置汇总：

| 处置 | 行数 | 占比 |
|---|---|---|
| 删除 | 55（12+18+10+15） | 46% |
| 迁 lint | 22 | 18% |
| 迁 CI / hook / deny | 15（9+6） | 13% |
| 迁 docs + 留指针 | 20 | 17% |
| 保留并改写 | 8 | 7% |

**120 行 → 约 12 行正文 + 3 条指针。**

这个结果不是"砍到 10% 所以更好"，而是：**90% 的内容并没有消失，它们只是搬到了遵循率 100% 的地方，或者搬到了按需加载的地方。** 真正被丢弃的只有 46%——那部分本来就是冗余和噪音。

这就是债务模型的实操版本：**你不是在删文档，你是在还债。** 每迁走一段，就有一处不可读被修好；每删掉一段，就有一张欠条被确认从来不需要。

### 5.4 你可以直接执行的最小流程

如果不想读完整篇再动手，这是最小可行版本：

1. **打印**你的 AGENTS.md（真的打印，或者开一个只读窗口）。
2. **每行贴四道过滤器**，在行尾写四个字母：`F1✓ F2✗` 这样。
3. **给每个 ✗ 写处置目标**：lint / CI / hook / docs / 删。
4. **改完看 diff 行数**。如果行数没降，说明你在重写而不是在还债。
5. **一个月后再跑一次**。如果这一轮没有可删的，要么你的仓库已经很健康，要么你在自我欺骗。

第 5 步是关键。**一次审计是清理，周期性审计才是机制。**

## 6. 薄厚之争是个伪问题：条件化的处方

### 6.1 一个被误读的结论

2026 年 2 月，OpenAI 发了一篇工程博客，讲他们团队五个月、零手写代码、约百万行、约 1500 个 PR 的实验。里面关于 AGENTS.md 的几段被广泛引用：

> "One of the earliest lessons we learned was simple: **give Codex a map, not a 1,000-page instruction manual.**"
>
> "So instead of treating `AGENTS.md` as the encyclopedia, we treat it as **the table of contents.**"
>
> "A short `AGENTS.md` (roughly 100 lines) is injected into context and serves primarily as a map, with pointers to deeper sources of truth elsewhere."
>
> （[Harness engineering](https://openai.com/index/harness-engineering/)，2026-02-11）

于是"约 100 行、只做地图"成了一个到处被复制的目标。

但同一篇文章里还有两句，复制者往往不引：

> "**Too much guidance becomes *non-guidance*.** When everything is 'important,' nothing is."
>
> "**It rots instantly.** A monolithic manual turns into a graveyard of stale rules. Agents can't tell what's still true, humans stop maintaining it, and the file quietly becomes an attractive nuisance."

而最关键的是他们**怎么做到**的：

> "We enforce this mechanically. Dedicated linters and CI jobs validate that the knowledge base is up to date, cross-linked, and structured correctly. A recurring 'doc-gardening' agent scans for stale or obsolete documentation that does not reflect the real code behavior and opens fix-up pull requests."

以及：

> "Because the lints are custom, we write the error messages to inject remediation instructions into agent context."

读到这里应该能看出问题：**"100 行地图"不是一个起点，是一个终点。** 它的前提是仓库里已经有一套可信的深层真相源、一套自写 linter、一套 CI 校验、以及一个定期巡检的 agent。

把这些前提拿掉，只保留"100 行"，你得到的是**一张指向虚空的地图**。

### 6.2 为什么"薄"有前提

薄的前提是：**地图指向的地方真的有东西，而且那里的东西比地图更可靠。**

如果满足这个前提，薄是对的——因为深层信息可以按需加载（渐进披露），常驻部分只承担路由功能，注意力预算被省下来了。

如果不满足这个前提，薄是错的，而且错得比"厚"更严重：

- **厚而错**：agent 读到一条过时的规则，做错了，但至少它有一条线索，你能通过"它为什么这么做"追溯到那条规则。
- **薄而空**：agent 什么都没读到，于是按它对"一般项目"的先验去猜。你既不知道它猜了什么，也没有线索可追。

**第二种失败更隐蔽，因为你连纠错的对象都没有。**

所以"薄 vs 厚"不是风格选择，是**仓库状态的因变量**。问"我该写多厚"这个问题的正确形式是："我的仓库现在处于什么状态，因此它需要多厚？"

### 6.3 一个成熟度模型

用两个轴来描述仓库状态：

- **X 轴：文档可信度**——`docs/` 是否覆盖架构、决策、边界？是否与代码同步？
- **Y 轴：机械化程度**——lint / 类型 / CI / test 的覆盖度如何？

四个象限，四种处方：

| | **机械化程度高** | **机械化程度低** |
|---|---|---|
| **文档可信度高** | **① 可薄**：约 100 行地图 + 闸门指针 + 验证命令置顶。这是 OpenAI 那个案例所在的位置 | **② 薄地图 + 优先补闸门**：地图可以薄，但你必须尽快把硬约束机械化，因为在这个象限里，68% 的文本约束是最贵的 |
| **文档可信度低** | **③ 中厚**：架构与决策背景必须显式写进文件，但每条要带"最后验证日期"和"何时该删"的退出条件 | **④ 先别写**：写 AGENTS.md 是在给一个不可读的仓库加注解，而注解会立刻腐化 |

**象限 ③ 是最容易被误解的。** 很多人看到"要薄"就去删，但他们在象限 ③——文档不可信。这时候删掉架构说明，等于把唯一一份还算准确的信息也丢了。正确动作是**保留但标注时效**，同时并行推进文档建设。

**象限 ④ 是本文最想强调的。** 它对应一个很常见的真实场景：一个小团队、没有 CI、测试要手动跑、`README` 停在两年前。在这种仓库里写一份漂亮的 AGENTS.md，效果是把 46% 的噪音和 54% 的临时欠条一起塞进上下文，然后在三个月内全部过期。

### 6.4 什么情况下你不该写 AGENTS.md

明确列出来，因为这四句话比任何正面建议都省时间：

1. **测试不是一条命令能跑完的。** 那么 AGENTS.md 里最该写的那一行你写不出来，剩下的都是次要信息。
2. **没有 CI。** 那么所有硬约束都只能停在 68%，而你会误以为它们是 100%。
3. **`docs/` 与代码脱节。** 那么"留个指针"会指向错误的地方，比不留更糟。
4. **没有 lint。** 那么风格约定只能写在文本里，而它恰好是最该机械化的部分。

如果命中任意一条，正确的顺序是：

> **一条能跑全量的测试命令 > CI 红灯 > lint > docs 骨架 > 最后才是 AGENTS.md**

这个顺序不是随便排的。它按"修好一处能删掉多少行"排序：一条测试命令能删掉整个"怎么验证"的段落；CI 能删掉整个"提交规范"的段落；lint 能删掉整个"代码风格"的段落。

**先修仓库，再写文件。** 这是债务模型的直接推论——你不可能靠写欠条来还债。

### 6.5 ETH 的实验和 OpenAI 的做法为什么不矛盾

这里有个表面矛盾必须解释，否则读者会觉得两边打架。

- ETH 论文说：LLM 生成上下文文件比手写差 7%。
- OpenAI 说：他们用一个 doc-gardening agent 定期扫描并提 PR 修复过时文档，效果很好。

矛盾吗？不矛盾。差别在**生成 vs 校验**：

| | ETH 实验里的 LLM | OpenAI 的 gardening agent |
|---|---|---|
| 任务性质 | **作者**：从零生成一份上下文文件 | **审稿人**：检查已有文档是否与代码一致 |
| 是否有可判定标准 | 无（"写得好不好"无法判定） | 有（"文档说的和代码做的是否一致"可以判定） |
| 输出 | 一份新文件 | 一个 diff / 一个 PR |
| 错误如何被发现 | 只能靠下游任务成功率（噪声极大） | 靠比对（信号清晰） |

**同一个模型，当作者时是 −7%，当审稿人时是正收益。** 这个区分极其重要，因为它给出了"AI 能不能维护 AGENTS.md"这个争议的答案：

> **可以让 agent 校验，不要让 agent 创作。**

校验有 ground truth（代码），创作没有。任何没有 ground truth 的生成任务，都会退化成"看起来合理"，而这正是第 2 章那个"看起来完成了"的同构问题。

### 6.6 三个未解争议

诚实地把没有定论的部分摆出来。

**争议一：薄指针 vs 厚自包含。**
本文的立场是"取决于象限"，但这只是一个工程折中，不是原理性答案。真正的分歧在于：**按需加载的可靠性有多高？** 如果 agent 在需要时总能准确找到深层文档，薄是对的；如果它经常找不到（或者找到了但没读），厚是对的。目前没有对照实验回答这个问题。

**争议二：agent 自维护的边界。**
6.5 节给出了"校验可以、创作不行"的判据，但边界仍然模糊。比如"把 review 评论自动转成规则"算创作还是校验？它介于两者之间——有信号源（人的评论），但输出是新规则。这类半结构化任务的可靠性还没有系统研究。

**争议三：采用量能不能当证据。**
本文的立场是不能。但反方有一个合理论点：**大规模采用会带来生态压力**，使得"不写 AGENTS.md"变成一种摩擦（工具会提示你缺文件、同事会问你为什么没有）。这种压力是真实的，只是它属于**协调成本**，不属于**效果收益**。把两者分开陈述是诚实的做法。

### 6.7 处方是一个函数，不是一张清单

本章的结论可以写成一个函数：

```
输入：仓库状态（文档可信度, 机械化程度, 私有事实密度）
      ↓
输出：文件形态（行数量级, 内容类型配比, 迁移优先级）
```

这个函数的好处是：**模型升级后你不需要重写它，只需要重跑它。**

因为它的输入是仓库状态，不是"当前最佳实践"。当模型变强时，变化的是"哪些信息算私有事实"这个判断（通用知识那一栏会缩小），函数本身不变。

这就是债务模型相对于清单的核心优势，也回答了最初那个焦虑：**你不需要追着模型跑，你只需要定期重新计算你欠了什么。**

## 7. 2026 年的写法：一台持续删除的机器

### 7.1 四道过滤器的执行流程

把第 3 章的表变成流程：

```
候选规则
  ↓
F1 不可推导？ ── 否 ──→ 删除
  ↓ 是
F2 改变动作/完成判定？ ── 否 ──→ 删除
  ↓ 是
F3 私有事实？ ── 否 ──→ 改写成私有事实，改不了则删除
  ↓ 是
F4 可机械化？ ── 是 ──→ 迁出（lint / CI / hook / deny）
  ↓ 否
保留
```

三个难判的边界，各给一个判法：

**边界一：「必须用 pnpm 不能用 npm」——留还是迁？**
先试 F4。能不能机械化？可以：`packageManager` 字段 + `engine-strict` + CI 检查 `package-lock.json` 是否存在。如果能拦住，迁；如果拦不住（比如有人在本地用 npm 装了包但没提交 lock），才留。**判法是"先试迁，迁不动才留"，不是"先留，出问题再说"。**

**边界二：「这个模块正在重构中」——算私有事实吗？**
算，但它是一张**短期欠条**。这类信息必须带两个字段：最后确认日期 + 退出条件（"重构完成后删除本节"）。没有退出条件的临时信息，会永久留在文件里，变成 OpenAI 说的 "graveyard of stale rules"。

**边界三：「不要写 `console.log`」——删、留还是迁？**
迁 lint（`no-console`）。这是一条零例外的规则，且完全可机械化。留在文本里只有 68%。

### 7.2 分层路由

四过滤器的输出不是"留/删"两态，而是五个去处：

| 层 | 放什么 | 判据 | 反例 |
|---|---|---|---|
| **常驻 AGENTS.md** | 每次都要用 + 不可机械化 + 私有事实 | 同时过 F1–F4 | 代码风格（应迁 lint） |
| **路径级规则**（`.cursor/rules` 的 `globs`、`.claude/rules` 的 `paths`） | 只对某类文件生效的约定 | 有明确路径边界 | 全仓库通用规则（不该限定路径） |
| **Skill**（`SKILL.md`） | 长流程、多步骤、只在特定任务用 | 步骤 > 5 且非每次触发 | 一行命令（应留在常驻） |
| **lint / CI / hook / deny** | 零例外的硬约束 | F4 不通过 | 有例外的偏好（应留文本） |
| **`docs/` + 指针** | 深层真相、架构决策、历史背景 | 需要时才读，且体量大 | 一行命令（不该埋进 docs） |

这一层的关键认知是：**AGENTS.md 不是唯一的载体，它只是"每次都要用"的那一层。** 一旦你有了这五层，文件变薄就不是靠删，而是靠**分流**。

Skill 这一层值得单独说一句。它的机制是**渐进披露**：常驻上下文里只放几十个 token 的元数据（名字 + 一句话描述），正文和捆绑文件在需要时才加载。Simon Willison 对此的判断是"maybe a bigger deal than MCP"，核心理由就是 token 效率（[simonwillison.net](https://simonwillison.net/2025/Oct/16/claude-skills/)）。Anthropic 自己的表述是三级披露：metadata → 正文 → 捆绑文件（[Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)）。

对你的直接含义：**任何"只在做 X 时才需要"的长内容，都不该常驻 AGENTS.md。** 它该是一个 skill。

### 7.3 一个约 100 行的结构

这是象限 ①（文档可信度高 + 机械化程度高）的形态。注意它**按价值密度排序，不按逻辑顺序排序**——验证命令在最前面，而不是像大多数文件那样放在最后。

```markdown
# AGENTS.md

## 0. 验证（改完必跑，不通过不算完成）
- 单文件：`pnpm vitest run <path>`
- 单用例：`pnpm vitest run -t "<name>"`
- 全量：`pnpm turbo run test --filter <pkg> && pnpm lint --filter <pkg>`
- 类型：`pnpm tsc --noEmit`
- 期望：全绿 0 error。失败先看第一条 error 的行号，
  先判断是实现错了还是断言错了，不要先改断言。

## 1. 硬约束（由机器强制，此处仅告知）
- 提交前必须通过 CI 的 `verify` job（含 lint / type / test / commitlint）
- `vendor/`、`migrations/` 由 CODEOWNERS 保护，改动需 @platform 批准
- 不得读取 `.env*`（已配置 deny rule）

## 2. 会误导你的地方
- `legacy/report/` 看起来废弃，但夜间报表任务在依赖它
- `src/utils/date.ts` 里的 `formatV2` 是旧模式，新代码不要模仿，
  用 `src/lib/time.ts`
- `packages/ui` 的组件不能直接引 `@/` 别名，会破坏构建

## 3. 不在代码里的决定
- 所有对外错误用 `AppError`（`src/lib/errors.ts`），带 `code` 字段
- 部署走 `make deploy-staging`，直连生产会被 WAF 拦 → [runbook](docs/runbook.md)
- 涉及 schema 变更必须附迁移计划，评审在 #platform-review

## 4. 深层文档（按需读，不要在这里复述）
- 架构与分层：[docs/architecture.md](docs/architecture.md)
- 关键决策记录：[docs/adr/](docs/adr/)
- 本地环境与故障排查：[docs/dev-setup.md](docs/dev-setup.md)

## 5. 本文件不写什么
- 不写代码风格（由 ESLint / Ruff 强制）
- 不写目录结构（`ls` 即可，且会过期）
- 不写技术栈版本（`package.json` 是唯一真相源）
- 不写"确保代码质量"这类无法执行的表述
```

约 40 行。剩下到 100 行的空间，留给"你已经被纠正过两次的事"——那是 Anthropic 正向清单的第 4 条，也是唯一一条**必须由你的实际失败经历填充**的内容。

第 5 节"本文件不写什么"看起来多余，但它是**唯一能防止后人加回来的机制**。没有它，三个月后一定有人把项目概览补回去。

### 7.4 维护的第一性原理：反馈不对称

现在到了全文最难的一节。

所有关于 AGENTS.md 的文章都会说"要定期更新"。这是一句正确的废话，因为它没有回答：**为什么它一定会腐化？**

答案不是"没人管"，而是一个结构性的不对称：

> **人类写一次，机器每天读。**
> 规则失效时，受害的是 agent 的任务成功率，而人类感知不到。

这是一个典型的**委托-代理问题**。写规则的人不承担规则失效的成本；承担成本的是每一次 agent 运行，而它不会抱怨。

具体表现：

- 你改了部署命令，AGENTS.md 里还是旧的。agent 照着旧命令跑，失败，然后**自己绕过去了**——它不会告诉你"你的文档错了"，它会自己想办法完成任务。于是你永远不会知道那条规则已经失效。
- 你加了一条 lint 规则，AGENTS.md 里还留着同样的文字。agent 会同时遵守两遍，多花一点 token，你看不见。
- 模型变强了，某条规则不再必要。agent 照做，多做一个无用步骤，你看不见。

三种情况里，**没有一种会在你的界面上产生任何提示**。这就是为什么"记得更新"这个方案必然失败——它要求人对抗一个没有反馈的系统。

### 7.5 三个结构性解法

针对反馈不对称的三个断点，各给一个解法。

**解法一：让失效可观测。**

在 CI 里真的去执行 AGENTS.md 里写的每条命令。跑不通就红灯。

这条做起来比听起来简单：把文件里的命令抽成一个可执行的 checklist 脚本（哪怕是手工维护的 `verify-docs.sh`），CI 每次跑。任何一条命令失效（命令改名了、脚本删了、参数变了），构建就失败。

这一步把"文档"变成了"有测试的文档"。而一旦它有测试，它就有了和代码一样的保鲜机制。

**解法二：让 agent 成为报告者。**

在任务结束时（或失败时）要求 agent 回答一个问题：**"这次任务里，有没有哪条规则误导了你，或者已经不适用？"**

这条目前没有成熟的工具支持，属于**本文的提议**，需要你自己在 prompt 或 hook 里实现。但它的机制是对的：把原本完全隐性的成本，转成显性的信号。

要注意的是，这个信号会有噪声（agent 可能编造"某条规则误导了我"），所以它应该是**候选池**而不是直接修改——收集一批，人工确认，再改。

**解法三：让删除成为默认动作。**

给每条规则带一个"最后验证日期"。超过 N 个月没有复验的规则，自动进入候选删除区。

这条的关键不是日期本身，而是**举证责任的转移**：

> **默认是删。保留需要理由。**

现在的默认是反的：规则一旦写进去就默认永久有效，删除需要理由。这个默认值必须翻转，因为腐化的方向是单向的——文件只会变厚，不会自己变薄。

Cursor 的文档里有一句话正好支持这个立场：

> "Start simple. Add rules only when you notice Agent making the same mistake repeatedly. Don't over-optimize before you understand your patterns."

以及一句更直接的：**"When you see Agent make a mistake, update the rule."**

注意这两句的隐含顺序：**先犯错，再写规则。** 而不是先写一份全面的规则，再等着犯错。这个顺序保证了每一条规则都有一个具体的、可追溯的失败作为它的"债权人"——**没有债权人的欠条，就是纯粹的负债。**

### 7.6 行数随时间的健康曲线

把债务模型画成一条曲线，可以诊断组织的病因。

健康的形态：**单调下降，然后趋于平稳。**

- 初期（0–3 个月）：快速下降。因为大部分内容是冗余，删起来没有阻力。
- 中期（3–12 个月）：缓慢下降。剩下的是真债，要靠修仓库来还（加 lint、收测试命令、写 ADR）。
- 后期：趋于平稳。此时文件里只剩私有事实和验证命令，它们不衰减，也不会增加。

三种病态：

| 形态 | 表现 | 病因 |
|---|---|---|
| **持续膨胀** | 行数逐年上升 | 没有删除机制；每次事故都加一条规则，从不合并、从不退役。规则在互相打架 |
| **长期停滞** | 行数纹丝不动，但仓库在变 | 文件已经变成装饰品。没人读它，也没人敢删它 |
| **反复震荡** | 大删一次，半年后又长回来 | 只做了清理，没做分流。删掉的内容没有迁到 lint/docs，于是以另一种形式回流 |

第三种最常见，也最能说明问题：**如果你删掉的内容没有去处，它一定会回来。**

这也是为什么第 7.2 节的分层路由比"删"更重要——删是动作，分流是结构。没有结构，动作会被逆转。

### 7.7 如果只能做两件事

最后给两个最小动作，按优先级：

**如果只能改一件事：让测试变成一条命令。**

它同时通过 F2（改变完成判定）和 F4 的反面（无法完全机械化），而且**永不衰减**——它描述的是你的仓库，不是通用知识。第 2 章那 7% 的差距，很大一部分就来自这里。Anthropic 的说法是："如果你仓库里已经有这样一个检查，那么 `CLAUDE.md` 里最有用的一行就是跑它的命令。"

**如果只能删一件事：删掉项目概览。**

它同时违反 F1（agent 自己读得到）和 F3（通用知识，快衰减），而且它是存量里成本最高的一段——因为它通常最长、最像"文档"、最让人舍不得删。厂商已经把它明确列进过时清单，实验也测不出它的贡献。

这两件事加起来大概需要半天。半天之后，你的文件会短一截，agent 会便宜一点，而且你会第一次感觉到：**这个文件是可以变小的。**

那个感觉，就是这套方法真正想给你的东西。

## 附录 A：四道过滤器速查

| 过滤器 | 一句话判据 | 通过 → | 不通过 → |
|---|---|---|---|
| **F1 不可推导性** | agent 能自己从代码里查到吗？它真的会去查吗？ | 继续 | **删** |
| **F2 决策相关性** | 它改变 agent 的动作，或改变"做完了"的判定吗？ | 继续 | **删** |
| **F3 低衰减性** | 这是本仓库的私有事实，还是通用知识？ | 继续 | **改写**成私有事实，改不了则删 |
| **F4 不可机械化** | 能被 lint / 类型 / CI / hook 强制吗？ | 保留 | **迁出**到闸门 |

三条铁律：

1. 四者是 **AND**，不是 OR。
2. 处置动作不同：F1/F2 删、F3 改写、F4 迁出。
3. 迁移优于删除——删掉的内容如果没有去处，一定会回来。

## 附录 B：一次性审计流程

**第一步：分类（30 分钟）**

把现有文件按段落切分，每段标注：概览 / 目录 / 技术栈 / 风格 / 验证 / 提交规范 / 禁令 / 架构 / 强调。

**第二步：过筛（每段 1 分钟）**

对每段贴 F1–F4，写下第一个不通过的过滤器。

**第三步：定处置（每段 2 分钟）**

| 第一个不通过的 | 处置 |
|---|---|
| F1 | 删除 |
| F2 | 删除 |
| F3 | 尝试改写；改不了则删除 |
| F4 | 迁到 lint / CI / hook / deny / docs |
| 全部通过 | 保留，并按价值密度重排（验证命令置顶） |

**第四步：验证（1 小时）**

把保留的每条命令真的跑一遍。跑不通的，要么改命令，要么说明它本来就不该在文件里。

**第五步：加护栏（30 分钟）**

- 加一节"本文件不写什么"
- 每条规则加"最后验证日期"
- 把可执行的命令抽成 `verify-docs.sh` 接进 CI

**第六步：一个月后重跑**

如果这一轮没有可删的，检查两件事：仓库是不是真的没变，或者你是不是在自我欺骗。
