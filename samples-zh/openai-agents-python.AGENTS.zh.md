# Agent 指令

## 权限与流程

- 在当前检出的工作区与分支上作业。新建或切换分支、worktree，需要就该动作取得明确批准——技能建议这么做时也一样。仅在获授权时提交；优先小而聚焦的提交，信息用简洁的祈使句。绝不 push、开 PR，或以任何方式改动 GitHub 上的状态。
- 已获授权的本地工作，要一路做到修复、评审、验证、交接完成。只有三种情况可以停：范围或契约上的决定悬而未决、缺少授权、外部阻塞；停时要指明缺的到底是哪个决定，以及哪条指令要求它。不要泛泛地请求"继续"的许可。
- 多步骤、多文件的工作，新功能，重构，或预计超过一小时的活，用 [PLANS.md](PLANS.md)。其中需要持续更新的小节要保持最新；工作量不小却有意省略时，说明理由。
- 状态标签：`RUNNING` 只用于进行中的说明；`COMPLETE` 表示所有适用的门禁与交接都已完成；`NEEDS_DECISION` 必须点出具体那个未决的决定或外部条件。

## 强制技能路由

技能位于 `.agents/skills/<name>/SKILL.md`。读选中的技能，以及它真正相关的支撑材料，别的不读。下表触发的只是"使用技能"的授权，不含额外的 Git 或外部动作。用户指令与已批准的范围，优先于技能的默认行为。

| 何时 | 必须做什么 |
| --- | --- |
| 改动或评审运行时行为、公开 API、配置、持久化 schema、线协议之前 | 使用 `implementation-strategy`；记录必需行为、兼容性、不支持的场景，以及一个已有的替代方案。只有当范围或实现形态变化时才重跑；独立评审者继承这份契约，遇到不确定就报告，而不是重跑策略。 |
| 对运行时、测试、示例、构建/测试行为或影响行为的文档做完聚焦检查之后 | 在展开全面终检之前，使用 `implementation-final-review`。评审分级与独立评审要求由该技能负责。规划、调查、纯报告类任务不适用。 |
| 编辑仓库元信息类指引 | 使用适用的技能校验；改动"决策类"指引时，需要贴近真实场景的检查，并额外过一遍独立评审。 |
| 改动 `src/agents/`、`tests/`、`examples/`、共享运行时工具，或 SDK 构建/测试配置（含 `pyproject.toml`、`Makefile`、`mkdocs.yml`、`docs/scripts/`、CI workflow） | 最后一组检查用 `code-change-verification`。命令顺序、容量检查、沙箱执行与重试由该技能负责。轻量评审不能免掉这道门禁。纯文档或仓库元信息类工作默认跳过，除非有人要求。 |
| 需要 OpenAI API/平台的权威事实时 | 使用 `openai-knowledge`。属于 SDK 自己的行为要在本地验证；没有变化的外部调研不要重复做。 |
| 运行时、测试、示例、构建/测试改动或影响行为的文档，评审与验证完成之后 | 使用 `pr-draft-summary`，未提交的工作也要用。编辑类、仓库元信息类工作，明确声明不用的，以及下面的发布交接，都跳过这一步。本地草稿不授予任何 Git 权限。 |
| 用户带着版本号明确调用 `release-candidate-prep` 时 | 按该技能执行，并过它的 `final-release-review` 门禁；它的报告替代通用 PR 草稿。上文关于检出与批准的规则，以及 [.github/RELEASING.md](.github/RELEASING.md)，同样适用。 |

## 范围与兼容性

- 用已有的事实来源，实现最小的受支持结果。新增抽象、选项、状态、校验、兜底、依赖或测试组合，都需要一个需求、一份已发布的契约、一条受支持的持久边界，或一处已验证的风险作为依据。已有组合能满足要求时，优先用它。
- 以下这些本身都不构成"受支持"：Python 层面的可构造性、手工损坏的类型化对象、被 monkeypatch 的状态、绕过公开边界或线协议的辅助函数调用，以及仅凭"某个已发布版本能复现"。这也包括非有限/极端数值和不可能出现的 enum/union 成员——除非存在受支持的产出方、已发布契约、持久边界或真实的不可信输入路径，使这一类成为相关问题。不要重复类型契约或上游校验，除非延迟拒绝会造成 SDK 自己要负责的后果：不可逆副作用、持久性损坏、安全或隐私暴露、本可避免的计费、重复资源消耗，或报错太晚、太含糊以致无法合理纠正。
- 兼容性只覆盖：最新已发布行为、明确支持的公开契约、受支持的持久外部状态与协议。对未发布的分支内接口（包括 `main` 上打 tag 之后的改动），优先直接替换，而不是加垫片；有意不支持的中间态持久化 schema，在发布前重新编号或压缩掉。若改动已发布行为或受支持的持久边界、且可能影响用户，先确认方案。
- 保持公开的位置参数与 dataclass 字段顺序；新增项只能追加。确实无法避免的重排，需要兼容层和覆盖旧调用方式的回归测试。调用处优先用关键字参数，但绝不能拿它当作破坏位置兼容的理由。保持既定的导入路径与 `__all__`；符号变化时同步更新再导出与导入测试。顶层导入不得因可选依赖缺失而失败，也不得产生运行时副作用。
- 若第二个相关问题又带出一个兼容性分支或一次协议跳转，触发"复杂度重置"：把根因归并，用 `implementation-strategy` 拿完整 diff 重新对照原始需求。优先删掉不受支持的机制，而不是继续加条件；已发布契约与无关改动要保住。

## 代码评审规则

| 方面 | 必须评审什么 |
| --- | --- |
| 范围 | 评审从目标 merge base 起的完整 diff；兼容性基线单独用最新发布版本。只报本次补丁引入、暴露或加重的后果，包括此前就存在、如今才被触达或被当作正确性依据的情况。只有当聚焦的改动无法做到正确、安全、兼容，或无法避免会出现可观察分歧的重复事实来源时，才要求更大范围的重构。 |
| 问题项 | 要给出受支持的触发条件，以及具体的、调用方可见的后果——兼容性、安全、持久化或生命周期上的。不要提推测性缺陷、审美偏好、无关清理，以及没有契约支撑的"对称性"。若证据不足以指向某份契约，就要求指出它与受支持行为或既有调用方预期的具体不一致。对于多余的机制，指明哪一处是不受支持的新增，以及最小安全删除方案或已有的替代。 |
| 契约覆盖 | 把改动过的公开值、配置值、事件值、序列化值与线协议值，沿受支持的构造、转发、适配器、默认/缺失/错误路径、消费、导出与生成包表面走一遍；在常规路径与专门路径上检查值是否被丢弃、改形，或被不一致地拒绝。只有已接受的需求或既有契约覆盖到的路径，才要求行为一致。 |
| 生命周期 | 在 await、回调、重试、重连、取消、清理与回滚处，检查过期或失败中的工作是否会覆盖、回退或释放仍然存活的状态。指出具体的交错时序，以及变更边界上缺失的归属、代次、身份、事务、复核或串行化不变量。部分获取之后、构造失败或上下文进入失败之后的清理，要单独验证；主失败必须保留。只报具体泄漏、过期状态、丢失的 handler 或幸存者损坏；顺序执行的顺风路径测试不足以证明。 |
| 测试 | 在最高、最稳定的调用方可见边界上验证，期望值来自需求、已发布行为、完整示例、基线或其他独立判据来源；只断言辅助函数的调用形状，证明不了另一层负责的结果。受支持行为与有意不支持的类别，都要有代表性的覆盖。并发回归需要可控的完成顺序，以及对幸存操作与最终状态的断言。避免镜像实现的断言，也避免穷举所有可构造组合。 |
| 就绪度 | lint、格式化、测试套件状态、提交历史、PR 描述的问题，与代码问题项分开列。检查通过，不能成为保留不受支持机制的理由。 |

文档是否必要、何时交付，按下面的文档规则判断，评审时也一样。

## 安全检查清单

读 [CONTRIBUTING.md 的安全检查清单](CONTRIBUTING.md#security-checklist) 并应用到受影响的路径；私下报告用 [SECURITY.md](SECURITY.md)。密钥与测试夹具、依赖、CI 权限、发布、披露与例外要求，以那两个文件为准。报告要写清评审过的边界、做过的检查、未解决的缺口；把已验证的控制与"只是政策要求"或"拿不到证据"区分开。

SDK 专项检查：

- 一条安全问题必须给出完整链路：从攻击者可控的输入，穿过真实的信任边界，到被保护的资产；只贴一个"安全"标签不算。

- 模型、工具、MCP 的响应，远程内容，manifest 与持久化状态，一律当作数据，而不是对宿主机安全、凭据、身份、清理或执行的授权。只有明确受支持的信任边界才能授予这种权力。保留受信任的当前配置，并在产生副作用、重放或做资源归属判断之前，先校验不可信状态。
- 不可信的沙箱 manifest 无权豁免宿主机的文件系统与基目录边界；实例化时的"逃生口"只能由受信任的调用代码提供。对每一条被声明的路径逐一核对授权，包括 `LocalDir`、`LocalFile` 与压缩包解包。
- 检查载荷脱敏是否覆盖异常对象、异常链、`__context__`、traceback、日志、遥测、会话状态、URL 与产物。`raise ... from None` 抑制的是显示，不是原异常里留存的敏感数据。

## 文档

### 文档的发布时机

只有在三种情况下才要求补文档或示例：既有指引变得错误、不安全或误导；正确用法需要一条不显然的约束、迁移步骤、兼容边界或警告；否则该功能实际上没法用。

描述"最新发布版里还没有的行为"的 `docs/` 内容，应另开一次纯文档工作、单独安排时间，不放进功能/修复 PR。把它记下来即可，既不算缺失的交付物，也不作为阻塞评审的问题项。这一条优先于技能与评审里的"文档完整性"规则。已经准确的已发布指引仍在范围内；示例与代码级文档不自动延后。

### 文档验证分级

按完整 diff 触及的最高一级执行。

| 级别 | 触发条件 | 检查 |
| --- | --- | --- |
| 编辑性 | 拼写、术语、标点、格式或链接文字的改动，且不涉及行为、可运行代码、导航、链接目标、锚点或生成的参考内容 | 看 diff，搜索被修正的文字，跑 `git diff --check`；若涉及链接或锚点则一并检查。跳过 `implementation-final-review`、跨语言评审与站点构建。 |
| 内容性 | 行为指引、迁移说明或可运行片段，且没有结构或工具链改动 | 对照实现或权威来源核实说法；条件允许时验证片段；执行下面针对性的跨语言评审；内容稳定后跑一次 `make build-docs`。 |
| 结构性 | 页面增删移动、导航、生成的参考内容输入、文档脚本/插件/构建配置 | 跑相关生成器与针对性检查，稳定后跑 `make build-docs`。属于构建/测试路径的，执行 SDK 终检。 |

评估构建退出码，以及由 diff 引起的错误、失效引用与警告；与本次无关的既有警告不算问题项。只有内容变了或仍有未解决的疑虑时，才重跑已通过的检查。`make build-full-docs` 与生成式翻译，留给翻译工具链改动、明确的本地化需求，或被要求的全量本地化审计。

- 不要编辑生成的 `docs/ja`、`docs/ko`、`docs/zh` 页面。
- `docs/` 下新增或大幅重写的可翻译英文（生成的 API 参考除外），要把有后果的行为主体、范围、归属、顺序、语气强度与生命周期边界写明确；行内代码里的 API 标识符保持原样。为便于翻译而澄清歧义代词、过载术语与简写时，不得改变被记录的行为。请独立评审者，或专门过一遍，聚焦改动句子及其上下文在日、韩、中三种语言里的歧义风险。具体问题要解决，改完的句子复查一次。不改变含义的编辑性改动跳过这道评审。
- 仍有歧义时，只临时翻译有争议的那一段；不要提交生成的本地化文件。修改固定的译名映射，必须有跨文档证据表明该术语已稳定；优先给上下文指引和既有的开发者术语（包括直接用英文），而不是维护一张庞大僵硬的映射表。
- 可运行片段要对照真实的构造器与 API 调用形状验证。示例与可运行文档中，SDK 装饰器从 `agents.decorators` 导入，优先 `tool` 而非 `function_tool`；其余导入保持在其公开路径上。

## 运行时参考索引

改动或评审运行时边界之前，先读[参考索引](.agents/references/README.md#reference-map)，再读受影响的那些参考。agents/上下文、runner/items、schema、工具、MCP、provider、会话/Session/RunState 持久化、追踪、Realtime、语音与沙箱生命周期的路由，都由那张索引负责。

- `src/agents/run.py` 只保留编排与公开流程；运行时辅助放进 `src/agents/run_internal/`。
- 工具的标准身份用 `src/agents/_tool_identity.py`，不要各自在本地做归一化。
- Realtime 追踪：提 span 方案之前先读映射到的那份架构参考。服务端 trace 与 SDK 客户端 trace 是分开的；`group_id` 只做关联，不构成共享层级。

## 测试与自动化检查

- Python 一律用 `uv run python ...` 执行；新检出或依赖变动后跑 `make sync`。命令与快照流程见 [tests/README.md](tests/README.md) 与 `Makefile`。
- 迭代期间用聚焦检查；评审干净之后，按技能表跑适用的终检门禁。内容未变时复用已通过的检查，除非出现失败或未解决的疑虑，确实需要再跑。
- 各自的工作流测试，优先用 `agents.testing.ScriptedModel`、`agents.realtime.testing.ScriptedRealtimeModel`、`agents.voice.testing` 里的工具，以及 `agents.testing.scripted_sandbox_session()`。要用专门替身，必须存在这些工具保不住、且写进文档的边界，例如 provider 线协议转换、畸形流、可控挂起/并发，或精确的取消与生命周期行为；并在测试里写明这条边界。
- 改动异步、重试、超时、子进程、PTY、警告或对 xdist 敏感的测试之前，先读[性能与确定性](tests/README.md#performance-and-determinism)；优化执行速度的同时，保住行为覆盖与生命周期覆盖。
- Python 注释写成完整句子，以句号结尾。正文不要按固定列宽硬折行；除格式要求换行的地方，一段就是源码里的一行。

## 可直接贴进 GitHub 的输出

用于发布就绪报告，或用户要求可直接粘进 GitHub 的文字（不含日常对话）：

- 给一个完整的、以 `markdown` 标注的围栏块，外层围栏比任何内层围栏都长，除非明确要求纯文本。不要再重复一遍渲染后的内容。
- 用合法的 GitHub Markdown，不要带本地绝对路径、Codex URI/指令、引用标记，也不要转义或嵌套的链接包装。宿主要求的注解放在围栏块外。行内代码用仓库相对路径，除非用户要求不给路径。
- 用原生引用：本仓库写 `#123`，别处写 `owner/repo#123`；保留 `Fixes`/`Resolves`。issue/PR 引用不要套 Markdown 链接。其他外部目标用带说明文字的链接。
- 检查真正可复制的那份文本，看标识符与链接有没有损坏。仅重排版的重发，保留此前评审过的提交与结论；它不意味着又做了一轮远程评审。
- PR 草稿用 [.github/PULL_REQUEST_TEMPLATE/pull_request_template.md](.github/PULL_REQUEST_TEMPLATE/pull_request_template.md)；包含摘要、测试计划，适用时附 issue 编号。
